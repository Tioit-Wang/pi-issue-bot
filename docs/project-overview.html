PROJECT OVERVIEW

pi-issue-bot

GitHub issue 自动处理平台：事件进、会话跑、结论写回、全过程可查。

形态
单进程 + 单 PostgreSQL
规模假设
< 100 事件/天
技术栈
Node 24 · Fastify · React
状态
已实现 · 未放行

1定位

一个跑在你自己机器上的 GitHub 机器人服务。它接 webhook、用 PostgreSQL 记事实、用 pg-boss 排队、用 pi-host 跑 agent、用 Docker 隔离命令，最后把结论写回 GitHub。

端点端口作用
POST /webhook3000GitHub App 投递入口：验签 → 去重 → 判定 → 入队，2 秒内应答
/api/*3000面板读接口（另含仓库设置、技能管理写接口）
/healthz3000健康聚合，任一检查 fail 返回 503
/metrics9464独立实例与 Registry，只监听 loopback

面板是纯前端 SPA，不连数据库、不 import 服务端代码，两侧只通过 packages/contract 与 openapi/pi-bot.openapi.json 耦合。

2解决什么问题

P1事件是散的

新建、编辑、打标、评论、关闭各算一次任务，agent 每次从零开始，正文重复注入、结论互不相认。

做法：一个 issue 一条会话（agent_sessions），后续事件进 agent_messages，同一 issue 同时只跑一条。
P2「要不要回」和「回什么」混在一起

让模型同时决定两件事，结果不可复现也无法解释。

做法：触发判定是纯函数（trigger/decide.ts），顺序固定，跳过原因落库。
P3写坏了没人兜

打错标、发错评论、推错分支，代价由人承担。

做法：dry-run 默认开；推送集 = 声明 ∩ 实际；代码里不存在 merge 能力。

3做与不做

做

  • 格式判定与模板回复（槽位覆盖，不刷屏）
  • 分类打标（六级归一，只撤自己打的）
  • @pi-bot /命令 执行技能
  • 建 issue（指纹去重 + 日配额）
  • 推 bot/* 分支、开 PR
  • 会话常驻 + 上下文压缩
  • 面板：吞吐 / 成本 / 改回率 / 审计 / 会话回放

不做

  • 不合并 PR（代码层无此能力）
  • 不设置信阈值（要证据，不要自评分）
  • 不做人工审批流
  • 不支持多租户 / GitLab / GHES
  • 不让 agent 直接写 GitHub

「不做」是设计决策，多数有机械约束：github/ 目录没有合并方法，apps/server/test/no-merge.test.ts 扫源码守住。

5一次事件

  1. 到达。GitHub 投递到 POST /webhook，raw body 保留。
  2. 验签。失败 401，并落审计。
  3. 投递去重。INSERT webhook_deliveries … ON CONFLICT DO NOTHING；rowCount = 0 直接 200 duplicate。
  4. 项目解析。找 repos 行、校验 installation_id；未知仓库也落审计。
  5. 判定。仓库开关 → 事件开关 → 附加条件 → 评论四闸门 → 内容去重 → 日配额；跳过就写 decision_reason 并 200。
  6. 落任务。INSERT tasks，command / actor_login / queued_at 写死。
  7. 入队。boss.send('run-task', {taskId}, {singletonKey: taskId, retryLimit: 0})。
  8. ack。打 eyes reaction（失败只 warn）后立刻 200。
  9. 领取。过全局并发（3）与仓库并发闸（默认 2）→ beginRun()。
  10. 准备。worktree 检出 → 起容器 → 起 exec 代理 → 等 pi-host ready。
  11. 执行。project/register → session/create → events/subscribe{after} → turn/start；事件先过三条熔断。
  12. 取结论。workspace/diff → 找信封 → zod 校验 → 写 envelopes（不合规也入库）。
  13. 写回。dry-run 只算不写；正式执行逐条动作，遇失败即停不回滚。
  14. 收尾。判定结局 → 销毁容器（先 inspect 采 OOM）→ 记用量 → 终态 reaction → 关 run。

同一 issue 的后续事件不走新 task 乱序：进 agent_messages，claimNextForIssue() 用 FOR UPDATE SKIP LOCKED 保证一个 issue 同时只有一条在跑。

6数据

27 张表（drizzle 定义 24 张 + 迁移建的 skills / skill_versions / skills_audit），12 个迁移，无外键，时间列一律 timestamptz。

7配置

7.1 项目级：repos.settings

仓库配置只有一个载体（.github/pi-bot.yml 已退役，解析函数无生产调用者）。默认值来自契约 repoSettingsSchema.parse({})；PI_BOT_DEFAULT_SETTINGS 只在建行时 seed 一次。

段内容
enabled / dry_run仓库总开关与写入开关
triggers.events五个事件各一档 on | conditional | off + 模板 + 附加条件；评论另有四闸门
labels词表、1:N 映射、白名单、互斥组、上限、meaning / managed / retired
limitsconcurrency_per_repo（1–8，默认 2）、queue_wait_minutes、max_comments_per_hour、max_actions_per_run、max_task_minutes
agentmanagers、技能绑定、project_prompt、system_prompt、动作开关（默认全 false）
agent.limitsdaily_quota（默认 100）、turn_timeout_minutes（1–30，默认 20）、data_retention_days

三条硬规则：写库前必校验（非法不写，保留 last-known-good）；archived_at 非空按 enabled=false；解析失败回默认值并给 ok:false，不抛错。

7.3 模板占位符

prompt/render.ts 只做字面替换 {{a.b}}：不隐式删行，未知占位符原样保留并收集到 unknown；{{repo.issues}} 惰性求值（仅 open、排除 PR、上限 200、5 分钟缓存）。所有插入的外部文本都经围栏中和后才进提示词。

8失败与重试

failure class优先级处理
timeout / interrupt / degenerate-output1不重试；超时先 turn/interrupt
sandbox-oom2不重试，必须先于 exitCode 判定
sandbox-crash3pg-boss retry 1 次
rate-limit4不用 retryLimit，用 startAfter（最多 4 次尝试）+ 两级窗口熔断（仓库 3 次/10 分钟，全局 5 次/15 分钟）
github-api（5xx）4retryLimit 3 / 30s / 退避
auth / parse / model4不重试

worker 不自己比较优先级，一律交给 pickHighestPrioritySignal()。命令级超时不是失败信号，只记在 failure_detail.commandTimeouts。

9边界与不变式

9.1 五条边界

边界约束与落点
凭证模型 key 与 GitHub token 只在宿主进程；pi-host 拿模型配置；容器内无凭证（app/model-env.ts、sandbox/hostconfig.ts、exec-proxy 不透传 env）
命令通道sandbox-bash → exec-client.mjs → exec-proxy → docker exec；帧只接受 {argv,cwd,clientPid}；找不到 socket 退 2，绝不回落宿主
容器只读根、CapDrop: ALL、no-new-privileges、uid 1001、tmpfs、AutoRemove: false（要先 inspect 读 OOM）；内存分档 2 / 4 GiB
网络deploy/nftables.conf 禁私网与云元数据、禁横向；只写不跑，需在目标机 apply 后用 doctor canary-network 复验
写回推送集 = declared ∩ actual；受保护路径或 .pi-bot/ 命中即整次失败；run-git.ts 每次检查 --force / --mirror

9.2 十条不变式

#不变式破坏后果
I1代码里不存在 merge 能力能力存在就会被调用
I2PI_BOT_DRY_RUN 默认 true安全变成「需要记得」
I3dry-run 零副作用（不写 actions）污染审计与改回统计
I4标签只撤自己打过的撤掉人打的标签
I5评论按槽位覆盖刷屏
I6幂等三层且不靠内存重投重复执行
I7会话状态只有 active / idle关单后无法重开复用
I8PIN 校验不放松bundle 可被替换
I9令牌加密存储，解密失败必须抛静默当成「没有令牌」
I10外部文本永远是数据提示词注入改变工具权限

已知弱点：approval-policy.ts 的 worktree 判断是字面路径前缀比较（符号链接靠 host-core 兜底），shell 判据是正则。改这里要连带改测试。

11术语

词含义
投递 / delivery一次 webhook 投递，webhook_deliveries 一行，幂等第一层
任务 / task一次要做的事，tasks 一行；source ∈ webhook|command|cron|agent
运行 / run任务的一次尝试，runs 一行，九步 TASK_STEPS
信封 / envelope模型产出的结构化结论：verdict + actions + usage
动作 / action写回意图：comment / label / create_issue / push_branch / open_pr / close_issue 等
目标态写回动作给「应该是什么」，由平台算 add / remove
槽位 / slot评论的逻辑位置，(repo, issue, slot) 唯一
会话 / session一个 issue 一条，active 或 idle
退化 / degeneracy段落重复、低新颖度、工具死循环；命中即中断不重试
RACPpi-host 的 JSON-RPC over WebSocket 协议，本项目只用 18 个 operation
PINbundle 清单：版本、wsPath、子协议、每个文件 sha256
技能 / skill一段可复用作业说明，放 .github/pi-bot/skills/**/*.md 或由面板上传
dry-run只算不写，默认开启
