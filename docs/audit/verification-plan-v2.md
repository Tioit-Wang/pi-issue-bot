## 0. 编制口径（先确认这三条理解）

1. **「分小节、分 session」**：以文档自身 h3 小节为最小单元，共 **29 个单元（U01–U29）**。§1 背景与问题不含可验证断言，**不设单元**（理由见 §6）。
2. **「两个实现互相不知道对方的存在」**：每个单元派 **2 个互盲 session（A / B）**。互盲靠三条硬约束维持（§2），不是靠善意。
3. **「至少两个 check session 交叉检查」**：2 个 check session 分区裁决，再互相交叉复核（§3）。

> 若你希望「一个小节只派 1 个 session」而不是 2 个，请指出——那会牺牲 §1 要求的互盲，与本次要求冲突。

## 2. 互盲协议（两个实现 session 之间的隔离机制）

### 2.1 硬约束（写进每个 session 的任务正文）

| 约束 | 具体措辞 |
|---|---|
| 只写自己的文件 | 「你的唯一产出物是 `<unit>/A.md`（或 `B.md`）。不得写、改、删任何其他文件。」 |
| 不读兄弟报告 | 「不得读取或列目录 `docs/audit/v2/` 下任何其他文件。只看代码与需求文档。」 |
| 不知道对方存在 | 任务正文**绝不出现**「另一个 session」「另一份报告」「交叉检查」等字样。不提 A/B 配对。 |
| 独立取证 | 「每条结论必须自带 `file:line` 证据。不得引用未亲自读过的内容。」 |

### 2.2 编排侧的纪律（我执行，不可省）

- 派发 A 时，**不把 A 的任何输出**喂给 B 的 prompt。
- A、B 可以在同一批次并发派发，但**不共享上下文**。
- 若某单元 A 失败需补派，补派的是「A2」，**不告知它 A 失败的原因**（否则泄漏方向）。
- 汇总阶段前，我**不改写**任何一份报告。

### 2.3 报告格式（A/B 完全一致，便于后续机械比对）

```markdown
# <单元 ID> <小节名> · <A|B>

## 结论速览
| 条目 | 状态 | 一句话缺口 |

## 逐条
### <条目编号>
- 状态：已实现 / 部分实现 / 未实现 / 与需求冲突 / 无法判定
- 证据：<file>:<line> — <关键代码要点>
- 缺口：（仅部分/未/冲突时填写，写清缺哪个子条件、影响什么）
- 判定依据：（为什么这条证据足以支撑该状态）

## 本节整体结论
<3–5 句>

## 核查边界
- 是否执行了命令 / 是否连了 PG / 是否只读静态
- 未覆盖的条目及原因
```

## 3. Check session 设计（2 个 check + 互相交叉）

### 3.1 分区

| Check | 负责单元 | 消费输入 |
|---|---|---|
| CHECK-1 | U01–U15 | 该区间全部 `A.md` 与 `B.md` |
| CHECK-2 | U16–U29 | 该区间全部 `A.md` 与 `B.md` |

**分区目的**：让两份裁决互相独立产生，避免同一人先看到另一份裁决。

### 3.2 CHECK-1 / CHECK-2 任务内容

1. 对区间内每个单元，逐条并列 A 与 B 的状态。
2. 分成三类：
   - **收敛**：A、B 状态一致 → 抽验 A 与 B 各 1 条 `file:line` 证据是否真实存在（防「都错了」）。
   - **分歧**：状态不同 → 亲自读代码裁决，写明采信哪一侧及理由。
   - **证据失效**：引用的行号不存在或代码已变 → 标 `STALE` 并要求重核。
3. 产出 `<CHECK-i>.md`，含：区间结论表、分歧裁决表（含亲自取证）、`STALE` 清单。

### 3.3 交叉复核（满足「两个之间进行 session 交叉检查」）

派 **CROSS-1** 与 **CROSS-2** 两个 session：

| Session | 任务 |
|---|---|
| CROSS-1 | 读 CHECK-2 的产出，逐条质疑：裁决依据是否成立？`STALE` 判定是否过度？区间内是否有单元被漏掉？产出 `CROSS-1.md` |
| CROSS-2 | 读 CHECK-1 的产出，同法质疑，产出 `CROSS-2.md` |

**注意**：CROSS 只审对方的 CHECK 产出，**不重做对方的范围**——否则退化成第三次全量审查。

### 3.4 终局裁决

由我（编排侧）汇总：
- CHECK 与 CROSS 无异议 → 定稿。
- 仍有分歧 → 我亲自读代码裁决，并在终稿标注「编排侧裁决」及依据。
- 只有「需运行环境才能确认」的条目允许留在 `无法判定`，且必须逐条列出。

## 7. 状态与证据口径（所有 session 共用，防各自解释）

**五个合法状态**

| 状态 | 判定门槛 |
|---|---|
| 已实现 | 代码明确满足该条全部子条件，且能定位到实现路径（有测试更好，但非必需） |
| 部分实现 | 主体在，但需求明写的某个子条件缺失 → **必须点名缺哪个子条件** |
| 未实现 | 找不到实现 |
| 与需求冲突 | 代码行为与需求相反 → **必须指出哪一行反着来** |
| 无法判定 | 需运行环境（PG / Docker / 真模型）才能确认 |

**证据口径**

1. 只认 `file:line` + 代码要点，不认注释与文档的自述。
2. 严格区分「表里有列」与「有执行路径 / 有查询出口」——只后者算实现。这条在上一轮抓出了 `decision_reason` 只写不读等 3 处问题。
3. 引用测试时，区分「测试存在且断言具体」与「测试跑过且绿」。默认只声明前者。
4. 行号必须可核对；若与工作区不符（文件已改），标 `STALE`。

## 8. 各单元待核条目明细（执行时逐条对照，防漏核）

> 每个单元的任务正文必须列出这些条目，session 不得自行增减。编号用于报告里的「结论速览」表。

### U01 §2.1 目标
- G-1 一个 issue 只对应一个 agent 会话（同 issue 多次处理共享 session，历史可延续）
- G-2 事件是否触发、用哪套提示词由配置决定（改配置即改行为，不改代码）
- G-3 全过程可查（完整对话 / 每次工具调用 / token 消耗）
- G-4 平台按项目分区（平台级给默认、项目级可覆盖、不同仓库互不干扰）

### U02 §2.2 非目标（核查「确实没有该能力」）
- NG-1 不合并 PR
- NG-2 不做多代码托管平台（只 GitHub）
- NG-3 不做审批流（不设人卡点）
- NG-4 不做多租户
- NG-5 本期不处理 PR 事件（收到后按未触发留痕）

### U03 §3.1 角色（四类角色的声明动作是否有实现路径）
- ROLE-1 提交者：提 issue / 补信息 / 追问进展
- ROLE-2 维护者：打标 / 要求补充 / 关闭
- ROLE-3 平台配置者：改项目配置 / 调提示词模板
- ROLE-4 平台运维者：看后台 / 查会话 / 调并发与配额

### U04 §3.2 场景 A（新 issue 格式不合格）
- SA-1 收到 `issues.opened` 能进入判定
- SA-2 按项目配置判定触发
- SA-3 用该事件模板渲染指令
- SA-4 交给该 issue 的会话
- SA-5 平台不预设动作（无按事件类型硬编码的固定评论/标签）
- SA-6 端到端：评论（带槽位）与标签（目标态）能真正落到 GitHub

### U05 §3.3 场景 B（作者补充信息需复核）
- SB-1 收到 `issues.edited` 能进入判定
- SB-2 判定正文确实变了（只改标题/标签不触发）
- SB-3 复用场景 A 的会话
- SB-4 **只把变更部分与本轮指令发过去**（不重复整篇正文）
- SB-5 结论追加在原有评论下面（同槽位编辑而非新发）
- SB-6 agent 基于已有上下文给出增量结论

### U06 §3.4 场景 C（维护者评论追问）
- SC-1 收到 `issue_comment.created` 能进入判定
- SC-2 评论三闸门（提及 / 限定角色 / 已关闭）存在且顺序在开关之后
- SC-3 合法提及判定（@ + 关键词 + 分隔符）
- SC-4 进入同一会话而非新开
- SC-5 `{{comment.body}}` / `{{comment.author}}` 在该事件下可用
- SC-6 与场景 A 用不同槽位（互不覆盖）

### U07 §4.1 四部件与边界
- P4-1 配置 / 调度 / Agent / 记录 四块在代码结构上可辨认
- P4-2 **Agent 不直读配置**（配置由调度读取后传入）
- P4-3 **Agent 不直连 GitHub**（执行环境无 GitHub 凭证）
- P4-4 产出只回到调度（经契约校验后才执行）
- P4-5 配置改动不需要动 agent 代码

### U08 §5.1 事件接入
- FR-1.1 单一 HTTP 入口 / 四类事件 / 读原始请求体 / 读三个请求头
- FR-1.2 HMAC-SHA256 校验，失败 401 且**仍落库留痕**
