## 第 7 章 业务规则

### BR-1 会话唯一 — 状态：部分实现

**映射一对一（已实现）**
- `apps/server/src/db/schema.ts:658-686`：`agent_sessions` 主键 `(repo, issue_number)`（685 行），一个 issue 一行。
- `migrations/0006_agent.sql:27`：`PRIMARY KEY("repo","issue_number")`。
- `apps/server/src/agent/store.ts:156-163`：`saveSession` 是 `INSERT … ON CONFLICT (repo,issue_number) DO UPDATE`，不会出现两行。
- `apps/server/src/http/webhook-v21.ts:793-795`：会话行创建是 `ON CONFLICT ("repo","issue_number") DO NOTHING`。

**「同一时刻只能有一个活跃会话」（部分实现）**
- 同一行只有一个 `session_id`/`state`（`schema.ts:665,676`），且 `state` 只有 `active|idle`（`schema.ts:688-694`）——从数据形状上不可能有第二条活跃会话。
- 但「不允许并发创建」只有应用层两道闸：`agent/store.ts:109-112`（`NOT EXISTS(running)`）与 `queue/definitions.ts:152-158`（`agentDispatch.concurrency: 1`）。**没有 DB 级部分唯一索引或分布式锁**；`agent/dispatcher.ts:20-23` 自述「两个 dispatcher 真同时进 `claimOldest` 时仍可能各领到同一 issue 的不同消息」。
- 会话创建侧是「先 attach、失败再 create」：`runtime/turn-driver.ts:354-392`。同一 issue 若真有两条任务并发，会各自 `session/create`，`saveSession` 为 last-writer-wins UPSERT（`store.ts:156-163`），旧会话 id 被静默覆盖、无告警。

**缺口**：并发创建会话无数据库级防护；覆盖旧 session_id 无留痕。

### BR-2 串行消费 — 状态：已实现

- 同 issue 串行三道闸：
  1. `agent/store.ts:124-139` `claimOldest`：`UPDATE … WHERE (… ) IN (SELECT … WHERE repo=$1 AND issue_number=$2 AND status='queued' ORDER BY created_at LIMIT 1 FOR UPDATE SKIP LOCKED) AND NOT EXISTS (running)`；
  2. `agent/store.ts:106-115` `queuedIssues`：`status='queued' AND NOT EXISTS(running)`，按 `MIN(created_at)` 排序；
  3. `queue/definitions.ts:152-158` `agentDispatch` 并发 1（注释明写「不是性能取舍，是语义」）。
- 跨 issue 并行：claim SQL 按 `(repo, issue_number)` 取最老一条，不是全局单条；`agent/dispatcher.ts:167-179` 一轮遍历多个 issue（上限 `AGENT_DISPATCH_MAX_ISSUES`，`agent/constants.ts:11`），turn 由 `run-task`（`queue/definitions.ts:93-94` 并发 3）承接。
- 任务结束后立刻领本 issue 下一条：`agent/dispatcher.ts:192-206`；接线在 `app/compose.ts:1081-1086`。
- 测试：`apps/server/test/agent-serial-queue.test.ts:179-210`（同 issue 3 条消息状态 `['running','queued','queued']`，runs 区间不重叠）、`:212-219`（两 issue 同时 running）。

**缺口**：`queuedIssues` 带 `LIMIT`（默认 20），积压超限时新 issue 顺延到下一轮（FIFO，不饿死），属实现约束而非需求违背。

## 整体结论

**已实现（6 项）**：BR-2 串行消费、BR-8 配置即快照；第 8 章的事件投递（90 天）、会话、轮次、用量；第 9 章的规模、响应、可靠、安全、可维护。

**部分实现（9 项）**：BR-1（并发创建会话无库级防护）、BR-3（三层齐备但「上一轮失败不算重复」未实现，失败即永久静默）、BR-5（PR 评论进同一条会话命名空间）、BR-6（判定写入完整，但**没有任何查询端点/契约/面板**暴露 `decision_reason`）、BR-7（兜底只覆盖「信封不可信且有人话」，超时/OOM/模型失败无 issue 侧反馈）、BR-9（目录外拒打已有，但目录与 GitHub 无一致性校验，`current` 取自自家台账）、BR-10（「原主人」是推导出的一句自由文本，无 `removed_by`/删除原因列；v2.1 控制面路径不写 `bot_labels`）、BR-11（`managed` 只对 v2.1 生效）、BR-12（v2.0 删除路径不看 `meaning`）；第 8 章项目配置（无版本）、对话（90 天后不可回看）；第 9 章可追溯（用量不在 issue 维度）。

**与需求冲突（2 项）**：BR-4（事件消息每次内联整篇正文，与「不重复整篇正文」相反）；BR-11 的 `human-veto`（`workflows/normalize.ts:212-226,241-263` 把「我们自己删过的标签」永久拉黑，比「人工删除不构成永久否决」更严，且真正的 `issues.unlabeled` 人工删除根本没被识别）。

**未实现（0 项独立条目，但有 2 个子项按口径判未实现）**：BR-3 的「上一轮失败不算重复」；BR-6 的「可在后台查询」。

**最该先补的三个洞**：① `decision_reason` 的查询出口（一条只读 SQL + 一个 `GET` + 契约字段即可闭合 BR-6）；② 失败消息的可重投路径（把 `failed` 视为可重新入队，或幂等键排除失败轮）；③ 删除标签的结构化留痕（`bot_labels.removed_by` / `removed_reason`，并让控制面 v2.1 路径也走 ledger）。

**核查手法说明**：以上结论均以代码 + 行号为准；「表/列存在」与「真被执行」已分开判定（见 BR-6、BR-10）。本轮为静态核查，未执行测试命令；引用到的测试用例是仓库里已存在且断言具体的用例，未验证其当前是否全绿。
