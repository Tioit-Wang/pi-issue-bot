## 二、五个合法状态（只允许这五个值）

| 状态 | 判定门槛 |
|---|---|
| **已实现** | 代码明确满足该条**全部**子条件，且能定位到实现路径 |
| **部分实现** | 主体在，但需求明写的某个子条件缺失 → **必须点名缺哪个子条件** |
| **未实现** | 找不到实现 |
| **与需求冲突** | 代码行为与需求相反 → **必须指出哪一行反着来** |
| **无法判定** | 需运行环境（PG / Docker / 真模型 / 真 GitHub）才能确认 |

不允许出现「基本实现」「大体符合」等自造状态。若你想表达「主链路对但有瑕疵」，用**部分实现**并点名瑕疵。

## 三、证据口径（四条硬规则）

1. **只认代码**：`文件:行号` + 关键代码要点。不认注释、不认文档自述、不认模块头部的「本模块负责…」。
2. **区分「存在」与「生效」**：表里有列 ≠ 有执行路径；有字段 ≠ 被消费；有函数 ≠ 有调用方。**只有后者算实现**。
   - 反例：`decision_reason` 列存在且写入完整，但全仓无读取 → 需求「后台可查」判未实现。
3. **测试口径**：区分「测试存在且断言具体」与「测试跑过且绿」。默认只声明前者；若你实际执行了命令，必须在「核查边界」写明命令与结果。
4. **行号必须可核对**：若读到的内容与所述不符（文件已变），标 `STALE` 并说明。

## 五、A / B 两种视角

| 视角 | 任务性质 |
|---|---|
| **A** | 正面取证：默认需求合理，去找实现证据并判定状态 |
| **B** | 反证：**默认每条都没真正实现**，主动构造「如果它是假的会长什么样」的检查点，只有无争议证据才推翻假设。必须填「反证过程」列。 |

两种视角的**状态定义、证据口径、输出格式完全相同**，只有取证方向不同。这样结论才可比。

## 六、硬约束（违反即作废）

1. **只写自己的产出文件**。不得写、改、删任何其他文件。
2. **不得读取或列目录** `docs/audit/v2/` 下除 `_baseline.txt` 与 `_TASK-TEMPLATE.md` 外的任何文件。

5. **不扩大范围**：只核你被分配的条目。发现的其他问题写进「发现的额外问题」段，不要另开核查主线。
6. 最终回复正文给「状态 + 一句话缺口」的浓缩清单，**不超过 400 字**。

## 七、常见误判（务必避开）

| 易错点 | 正确做法 |
|---|---|
| 看到配置字段就判已实现 | 去追「谁读它、读了之后改变什么」；无消费方 = 死字段 |
| 看到函数就判已实现 | 去搜调用方；零调用方 = 死代码 |
| 看到测试文件就判已实现 | 打开看断言内容是否真的覆盖该条；只断言 200 不算覆盖 |
| 需求写「每次调用都带」，代码只在建会话时带 | 这是**部分实现**，不是已实现 |
| 需求写「不归档」，代码有 archive 分支 | 这是**与需求冲突**，并指出行号 |
| 需求数字（200 条 / 2000 字符 / 90 天）与代码常量不符 | 这是**与需求冲突**，列出两个数字 |
