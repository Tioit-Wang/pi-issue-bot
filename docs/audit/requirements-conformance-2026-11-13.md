## 最高优先级缺口（P0，按修复成本排序）

1. **BR-6 / FR-6.4③：`decision_reason` 只写不读** — 数据完整、枚举齐全，但 `queries/`、`http/api/`、契约、面板四处都没有查询路径。需求「被忽略的事件也能看到原因」完全落空。修复成本最低（一条只读 SQL + 一个 GET + 契约字段）。
2. **FR-5.6 上下文压缩：引擎是死代码** — `compact/` 六个文件的公式、六阶降级、2000/500 分层截断、空摘要判失败全部正确且有 79 例单测全绿，但 `compactSession()` **没有任何生产调用点**（三处注释自认「只暴露不调用」）。需求「超过模型窗口时必须自动压缩」未达成。
3. **FR-5.4 / BR-10：删除权与删除留痕双重失效** — `current`/`botLabels` 取自自家 `bot_labels` 而非 issue 实际标签，导致（a）人打的标签永不进 `remove`，（b）`deletionOwner` 恒为 `bot`，（c）装订层把承载 owner 的 `detail` 丢掉。`bot_labels` 无 `removed_by`/`removed_reason` 列。
4. **BR-3 / FR-3.5：上一轮失败被永久判重** — 失败消息仍占 `agent_messages` 主键，同内容重投命中 `ON CONFLICT DO NOTHING` 直接判 duplicate，全仓无 `failed → queued` 回滚路径。这正是需求第 917 行要防的事故。
5. **FR-3.5：内容级规范化越界** — `canonical-text.ts:30-36` 抹代码区 + 删标点符号 + 压换行，把「措辞不同就是不同内容」变成了「去标点就算同一内容」，与「不能把新问题误判成旧问题」正面冲突，且被测试固化。
6. **BR-4 / FR-4.2：增量投喂未实现** — 五个默认事件模板全部含 `{{issue.content}}` 全文，`issues.edited` 的 `changes` 只用于触发判定后即丢弃。两 session 独立确认全仓无「首轮/后续」判据。
7. **§5.7 面板整体未落地** — 需求点名要删的五个全局页（总览/成本/质量/审计/系统）在 `routes.tsx:55-59` 与 `nav.ts:22-28` 全部健在且 `nav: true`，测试还反向加固现状。这不是一轮前端改造能补的：原文卡、系统提示词、token/单价、verdict/actions、写回行多数是**契约层缺字段**。
8. **§6.8 / §6.9 整体未实现** — 供应商行、四档模型角色与单价、个人 PAT 身份切换与权限检查，代码与契约里没有对应实体，数据库无对应表。模型仍只有「一个 env 端点 + 写死两档价目」。
9. **BR-11 实现反了** — `workflows/normalize.ts:212-226,241-263` 把「最后一次 `removed_at` 非空」当 human-veto 永久不加回，而 `removed_at` 唯一写入方就是我们自己的成功删除。真正的 `issues.unlabeled` 人工删除根本没被接收（事件路由只映射 `labeled`）。
