## 二、FR-5.1 的裁决

### 2.1 裁决

**兜底评论这一层整层移除，不是「这次不发全文」。** 平台在产出不合契约、或产出合规但没给 `comment` 动作时，**一条评论都不发**，只留痕。

### 2.2 理由与证据

1. **「平台只做三件事」是穷举，不是举例。** `docs/requirements.html:960`：「平台只做三件事：把输入交给执行侧、校验产出、把产出执行出去。」合成评论是第四件事。
2. **是否补发由命令白名单决定 = 按事件类型硬编码行为。** 原实现 `supportsCommentFallback(command)` 只认四条命令（`worker/fallback.ts:47`），`agent:event` 补、别的命令不补。`docs/requirements.html:958` 明确「不按事件类型硬编码行为」——这不是措辞偏好，是需求点名的一条禁止项。
3. **`actions: []` 是合法的「只判定不动作」，补评论等于给动作集合开旁路。** `docs/requirements.html:1000`：「空数组表示只判定不动作」；`:1001` 要求类型「其他值一律拒绝」。平台自己补一条评论，就是自造了一个不在封闭集合里的动作来源。
4. **FR-5.5 直接把这条路的终点堵死。** `docs/requirements.html:1052-1058`：「执行侧没有产出（含输出不合契约）时，标签与评论**保持原状**。」补发评论就是「改变了原状」。
5. **BR-7 的「失败必须有可见反馈」由后半句满足，不需要靠兜底评论。** `docs/requirements.html:1792` 的原文是「兜底评论**或**后台告警」——是「或」。现在走的是后半：`failure_class=parse`（信封不合规）/ `run.outcome=succeeded` + `writeback.fallback-skipped`（合规但没动作），事件进 `run_events`，面板与告警都能查。留痕文案：`logger.info({ cause, command }, '平台不合成动作（FR-5.1）：本轮不写任何评论')`（`run-task.ts:1273`），`appendEvent('writeback.fallback-skipped', { reason, cause, command })`（`:1274`）。
6. **这个缺陷此前被 dry-run 默认开启遮住。** `PI_BOT_DRY_RUN` 默认 `true`（AGENTS I2），写回被闸门挡住，所以「平台自己发评论」在生产默认配置下看不出来；关掉 dry-run 才暴露。`docs/audit/v2/_adjudication.md:41` 记的正是这条链路的取证点。

### 2.3 移除后的行为口径（可观察事实）

| 情形 | run 结局 | issue 上的写回 | 留痕 |
|---|---|---|---|
| 信封不合规（含缺信封）+ 有人话 | `outcome=failed`、`failure_class=parse`、不重试 | **零评论、零 actions 行** | `writeback.fallback-skipped`，`cause='invalid-envelope'` |
| 信封合规但 `actions: []` | `outcome=succeeded`、`failure_class=null` | **零评论、零 actions 行** | `writeback.fallback-skipped`，`cause='no-comment-action'` |
| 信封合规且有 `comment` 动作 | 照旧 | 按槽位写回（FR-5.4 语义不变） | 不变 |

`report.fallback` 字段保留但**恒为 `null`**（`run-task.ts:1712`）。它是 `worker/types.ts:488` 的既有字段，删字段会牵动禁改文件，故只把它钉死为常量并在注释里写明去处（`:1707-1710`）。

## 三、FR-5.3 收敛明细

### 3.1 七类保留（需求表逐行对应）

| 需求表行（`docs/requirements.html`） | 动作 | 契约 `type` | 项目开关 |
|---|---|---|---|
| `:980` 判定 | 结论 + 证据 | `verdict` | 开放 |
| `:981` 标签 | 目标态标签全集 | `label` | 开放 |
| `:982` 评论 | 槽位名 + 正文 | `comment` | 开放 |
| `:983` reaction | 加 / 减 | `reaction` | 开放 |
| `:984` 建 issue | 标题 + 正文 + 初始标签 | `create_issue` | **默认关闭** |
| `:985` 开 PR | 分支名 + 标题 + 正文 | `open_pr` | **默认关闭** |
| `:986` 关闭 issue | 无（不带理由） | `close_issue` | **默认关闭** |

### 3.2 被移出集合的五类（逐条说明）

| 动作 | 为什么不在封闭集合里 |
|---|---|
| `reopen_issue` | 需求表没有这一行；它会改仓库可见状态（重开单）却**没有项目级开关**——七类里「三关闭」的边界被绕过 |
| `update_issue` | 同上：改标题/正文/指派/里程碑是可见状态变更，无开关 |
| `update_comment` | 改别人看得见的评论正文，无开关 |
| `delete_comment` | 删评论，无开关 |
| `link` | 需求表把它作为工具（`IssueLink`，`:1167`）而不是产出动作；v2.2 给它的 `relation:'duplicate'` 开了「等价于关单」的旁路，等于用一个不在表里的动作触发受开关约束的 `close_issue` |

### 3.3 为什么 schema 形状还留在 `packages/envelope/src/v21.ts`

这五类的 zod 形状留在文件里（`:372` 起），**唯一原因**是禁改文件 `apps/server/src/writeback/v21/execute.ts` 用 `switch (action.type)` 对 `OutputV21Action` 做类型收窄；删掉形状会让那个文件编译失败（`never` 收窄）。因此：

- 校验层是**唯一收口点**：`preflightDiscriminator()` 在最前面用 `isRemovedActionType()` 判死，错误落在 `/actions/<i>/type`，与「模型自创类型」分开报（`:571-587`）。
- 执行器里那五支成为**不可达死代码**——任何走生产入口的产出都过不去（`:44` 的注释就是这么写的）。这一点已登记为残余风险 R2，不是「看起来修好了」。

### 3.4 测试怎么钉住的

- `packages/envelope/test/v21.test.ts:194`：`REMOVED_ACTION_TYPES` 与 `OUTPUT_ACTION_TYPES` 不相交、且恰好是那五类。
- `:208`：封闭集合就是需求表的七类，**顺序一致**（顺序即提示词渲染顺序）。
- `:220`：五类逐个被拒，错误文案含「已不在 FR-5.3 的封闭集合里」且路径指到 `type`。
- `:231`：合法动作与被移除动作混在一份产出里 → **整份拒绝**（一条都不执行）。
- `:301`：`link` 不再被当成关单（它连产出都过不去）。
- `apps/server/test/writeback-v21-execute.test.ts:646`：五类动作在执行器之前就被拒；`:680`：七类仍然可执行（收敛没砍掉能力）。

- **`apps/server/src/skills/registry.ts` 保留**。它是**技能文件加载器**：把「内置 + 仓库自带」两批文件合成一张确定的命令表，判决覆盖与冲突（同名用仓库的、仓库内重名两者都不加载、frontmatter 非法不回落、`requires-repo-config` 缺配置不可用……见文件头 `:1-13`）。面板技能页要读它。它**不是**「事件 → 技能」映射，Q-6 针对的是后者。
- **`settings.agent.on_opened/on_edited` 留在契约里**（`packages/contract/src/repo-config.ts` 属禁改面），但**已无任何读取路径**：`grep` 全仓只剩注释与测试里的历史说明。这是残余风险 R5。

### 4.3 技能从哪来（AGENTS §11.1 分工）

事实（`owner/repo`、`issue#n`、标签、项目标签词表）由 `skills/prompt.ts` 用运行时真值渲染；方法（先调哪个工具、传什么参数）写在技能正文；动作走信封 `actions`。技能正文里不出现 `{{...}}` 占位符、不复制工具清单——`test/agent-skill-wiring.test.ts`（8 tests）仍全绿。

事件消息现在 `skillIds: []`，`renderSkillDirective([])` 返回空串（`message.ts:208-212`），所以事件消息正文里不会出现「按技能执行」段。用户自己写的 `/技能名` 不受影响（那是用户的显式选择，不是平台预设）。
