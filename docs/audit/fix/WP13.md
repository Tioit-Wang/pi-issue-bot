## 四、跳过项与残余风险

1. **C3 的代价从「1 次大页」变成「4 次小页」**：状态带每次刷新发 4 条 `limit=1` 的 `/api/issues`（queued / idle / running / failed）。选这个形状的理由：`totalEstimate` 与 `issues` 共用同一份服务端谓词，用它计数才不会与列表打架；而「拉一页再客户端分桶」在 >100 条时是**错的**（WP11 §六.3 的自述缺陷）。代价是 4 次往返而非 1 次 —— 每次 `limit=1`，服务端多出的成本主要是那份 `count(*)`（WP12 §五.3 已记账）。要进一步降需契约提供按状态分桶的聚合端点（WP12 §一 C3 的「未做」），属契约 owner。
2. **C4 的截断是面板侧的取舍，不是服务端限制**：`IssueTurn.actions` 仍会整段进响应（WP12 §五.2 已记账 ~1 MB 的极端情形）。面板只渲染前 4 000 字符并说明，但**网络传输与 JSON 解析的成本仍在**。要根治得契约侧加 `?envelope=summary` 或分页拉信封。
3. **C5 只读**：不改 key / 不加供应商 / 不改单价（写接口 + 密钥入参不在本包范围）。这是 `FR-7.5` 的形态，不是遗漏；但「全局设置」这个标题下用户可能期待可编辑 —— `system-settings.tsx:70` 的 `footnote` 已写清缺哪些接口。
