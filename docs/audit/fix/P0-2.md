# P0-2 上次失败不参与去重（消息失败被永久锁死）

- 缺陷（需求 `docs/requirements.html:917`）：「上次失败不参与去重——上一轮是超时、崩溃或未产出，等同内容再来一次视为重试，必须放行。否则一次故障会把这个内容永久锁死。」
- 实际行为：失败的消息仍占 `agent_messages` 主键 `(repo, issue_number, fingerprint)`，同内容重投命中 `ON CONFLICT DO NOTHING` → `inserted=false` → 上层直接判 duplicate，永久锁死。
- 改动面：`apps/server/src/agent/store.ts`（两处 SQL + 两处取值）与 `apps/server/test/agent-serial-queue.test.ts`（追加用例）。**未**动 `compose.ts` / `canonical-text.ts` / 需求文档 / 表结构 / 迁移。

## 1. 改了什么

### 1.1 `insertMessage`：`DO NOTHING` → 只对 `failed` 行 `DO UPDATE`（`store.ts:107-112`）

```sql
INSERT INTO "agent_messages" (... )
VALUES ($1, $2, $3, $4, 'queued', $5, $6, $7, $8::jsonb, now(), now())
ON CONFLICT ("repo", "issue_number", "fingerprint") DO UPDATE
SET "status" = 'queued', "updated_at" = now()
WHERE "agent_messages"."status" = 'failed'
RETURNING "created_at"
```

`inserted` 的判定不变（`store.ts:264-265`，`rowCount > 0`）：新插入出一行、命中 `failed` 重置出一行，两种都算「该处理一次」；命中 `queued` / `running` / `done` 时 `DO UPDATE` 的 `WHERE` 不成立 → 0 行 → 上层照旧判 duplicate。

### 1.2 `insertTask`：上一轮任务终态失败时把同一行重新置 `queued`（`store.ts:173-178`）

```sql
ON CONFLICT ("idempotency_key") DO UPDATE
SET "status" = 'queued', "updated_at" = now()
WHERE "tasks"."status" IN ('failed', 'timed-out')
RETURNING "id"
```

配套：`insertAgentTask` 回填 `RETURNING` 的 id 而不是 `input.taskId`（`store.ts:365-369`），这样命中可重跑的旧行时拿回的是**旧 id**（重跑同一行），而不是误报新 id。

## 2. 为什么这样改（对照需求 917 行）

1. **「失败不参与去重」= 既有行可被重置。** 去重的物理载体就是 `agent_messages` 的主键 + `ON CONFLICT DO NOTHING`，所以放行只能在冲突分支上开一个口子：`WHERE status = 'failed'`。
2. **口径边界严格按需求。** 需求 §5 同时要求「同一句话只处理一次」（L-01 / R-02），因此 `queued` / `running` / `done` **一律不重置**：`done` 是「已处理成功」，`queued` / `running` 是「正在进行中」，重置它们就等于重复烧钱。
3. **并发只放行一次。** `ON CONFLICT DO UPDATE` 会先锁住冲突行、再按**最新版本**重算 `WHERE`：两个并发重投里抢输的那个看到 `status='queued'` 就不再更新、返回 0 行 → 仍然判 duplicate。不依赖内存去重（AGENTS §9.4）。
4. **必须连带改 `tasks`（1.2 的理由）。** 只改 1.1 会**制造更糟的死锁**：消息被放行后 dispatcher 会 `claimNextForIssue` 把它置成 `running`，但 `insertAgentTask` 仍命中上一轮任务的 `tasks.idempotency_key`，`DO NOTHING` 后回填旧 id；dispatcher 见 id 非空即当「已投递」，不入队 → 这条 `running` 消息永远没有结束信号，而 `listQueuedIssueKeys` 会跳过「有 running 的消息」的 issue，**整个 issue 的串行队列一起卡死**（原缺陷只是这条内容锁死）。
   探针实测（脚本见 §3.3，**只改 1.1、不改 1.2 时**）：`4) 重投 inserted = true  status = queued` → `5) dispatcher 领到 = running` → `6) 出队建任务拿到 id = probe-task-1`（= 上一轮失败任务的 id，`DO NOTHING` 回填）→ `7) 消息状态 = [ { status: 'running' } ]`，之后无人再动它。
   改后同一探针：`6) 重试建任务拿到 id = probe-task-1` 且 `6b) 任务行 = [ { id: 'probe-task-1', status: 'queued', queued_at: ... } ]`，重跑交给 `run-task`。
5. **只改 `status` / `updated_at`。** `queued_at`、`command`、`actor_login` 是入队时写死的审计字段（AGENTS §7.4），一个都没动；「第几次尝试」由 `runs.attempt` 记。重跑同一 task 行是本仓库既有语义（`run-task.ts:1656` 注释：「锚点取 `tasks.idempotency_key`（不是 taskId）：重投/重跑不该重复打 reaction」；`/retry` 与 `decideRetry` 也是投同一 task）。
6. **`timed-out` 必须算失败。** 需求 917 原句就点了「超时」；`tasks.status` 里超时是独立终态 `timed-out`（`db/schema.ts:44`），只判 `'failed'` 会漏掉一半场景。
7. **`created_at` 不动。** 重试保留它在队列里的原始位置（`claimOldest` 按 `created_at` 排序），不会插到更新的消息前面乱序。

## 4. 未覆盖的风险 / 交给别人的缺口

### 4.1 `test/agent-serial-queue.test.ts:171` 的旧 L-02 现存红（**P0-3 的残留缺口，我没改**）

`normalizeForIdempotency` 已被并行会话按需求 §5 收窄成「只去首尾空白 + 合并连续空行」（`canonical-text.ts` 有未提交改动），于是 `'@pi-bot 打个标签'` 与 `'@pi-bot   打个标签！'` 现在是**不同内容**（实测 `equal: false`），该用例断言的 `duplicate` 不再成立。P0-3 报告里列了它改的 `agent-message.test.ts` / `v21-webhook-integration.test.ts`，**漏了这个文件**。建议按 P0-3 的口径改成「只差首尾空白与连续空行」的两句话（例如 `'@pi-bot 打个标签'` vs `'  @pi-bot 打个标签\n\n\n'`）。这属于归一化口径的决定，不在 P0-2 授权范围内，故只报不改。

### 4.2 任务重跑后的观测面

- `tasks.attempt` 不递增（本仓库把「第几次」记在 `runs.attempt`，`app/compose.ts:483` 用 `tasks.attempt + 1`）；重跑次数只在 `runs` 可见，面板按 `tasks` 看会显示同一条任务有多轮 run。
- `tasks.status` 会从终态 `failed` / `timed-out` 回到 `queued`：审计上「这一行曾失败过」只留在 `runs` 与 `run_events`，不在 `tasks.status`。若审计要求「终态不可回退」，需要另一套（新 task id + 带 attempt 的幂等键 + 同步改 `parseAgentTaskIdempotencyKey` 与回写解析），属于设计决策。
- 队列重投靠 pg-boss 的 `singletonKey = taskId`：若上一轮 job 仍留在 pg-boss 的 created/active 集合里，`send()` 会返回 `null`（`queue/boss.ts`），`dispatchNextForIssue` 只记日志不重试。失败任务正常已出队，但「进程崩溃时 job 仍 active」这一窗口没在真 pg-boss 上验证。

### 4.3 `insertMessage` 只重置状态，不刷新消息内容字段

同一 fingerprint 的另一条投递如果带了不同的 `comment_id` / `actor_login`（例如另一个人贴了同样的日志），重置后仍指向**第一次**那条评论与作者：回写 `@login` 与回复目标沿用旧值。需求只要求「放行」，未规定归属，故未改；若要求「以最新一次投递为准」，需要额外刷新这几列（会改「谁问的」这一审计口径）。

### 4.4 未覆盖的失败形态

- 测试用 `markMessage(..., 'failed')` 直接构造失败态，没有跑真正的「RACP 崩溃 / 容器 OOM / 任务超时」链路（那需要 Docker 与假 host，属 `agent-serial-queue.test.ts` 现有 e2e 用例的地盘）。失败态与 `tasks.status` 的对应关系（`failed`↔`failed`、超时↔`timed-out`）靠代码阅读，没有端到端用例钉住。
- 并发重投（两个相同 fingerprint 同时到达）只有 SQL 语义推理，没有并发用例；`query.agentDispatch` concurrency=1 也压低了这场景的实际概率。
- 未跑 `pnpm -r test`（面板与其它包）：本次没碰契约与面板，`store.ts` 不被面板引用。
