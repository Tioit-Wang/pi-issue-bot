# P0-1 会话轮换（归档换会话）

- 缺陷：`docs/requirements.html` FR-3.4 / 决策 Q-3 明写「会话**没有『结束』这个状态**……不归档、不释放映射」「issue 重开时直接复用原会话」。实际行为是 30 轮 / 7 天后先 `session/archive` 旧会话、再新建一条，历史永久断在轮换点；而且本该挡住它的「不归档」守卫挂在生产路径恒假。
- 方案：**方案 A —— 让会话永不轮换**（不是方案 B「把守卫修活」）。
- 改动面：`apps/server/src/app/compose.ts` 的会话计划 / 会话写回 / 归档调用三处；一个纯函数用例（新增）；一处过时注释。
- 未动：`panelDistDir` 注入（现在在 `:911-912`，别人的未提交改动，原样保留）、`canonical-text.ts`、`agent/store.ts`、`agent/session-state.ts`（那里本来就没有轮换判定，只有 `active`/`idle` 两态，无需改）、需求文档。

## 1. 为什么选 A 而不是 B

需求原文是**无限期**语义：「会话没有『结束』这个状态」「与该 issue 同生命周期」「重开时直接复用」。它不是一个「在什么条件下才不归档」的条件式规定，所以把守卫修活（方案 B）仍然留着一条「到点就断历史」的路，只是让它暂时走不到。

方案 A 是否会破坏别的逻辑 —— 查了三条可能的反证：

1. **上下文预算**：轮换从来不是上下文治理手段，需求已经把这件事单列成 FR-5.6（上下文压缩：阈值现算、追加不改写、分层截断工具输出、六阶降级）。用重建会话去「省上下文」的代价是历史不可恢复，压缩可以做到同样效果而不丢。
2. **成本 / 面板指标**：`agent_sessions.turns` 与 `started_at` 还在照常写（`turns` 只增不减、`started_at` 只在第一轮落），面板与统计口径不变，只是它们不再被当成阈值。
3. **跨 issue 隔离 / 串行**：与轮换无关（`agent-dispatch` 并发 1、按 issue 串行，FR-3.3）。

另外，修守卫（B）需要给 `onTaskJob` 造一个「真实事件 + issue 实时状态」的 `sessionEvent`，而队列侧既没有 `X-GitHub-Event` 也没有 issue 实时状态 —— 造出来的只能是假事件，等于把「权威写入在 webhook 侧」这条互斥约定也一起破坏掉。A 的改动面反而更小、更诚实。

## 5. 残余风险

1. **上下文会无限增长**。会话不再重建，一条长命 issue 的历史只会越来越长；压这个增长的责任在 **FR-5.6 上下文压缩**，当前 `executeTask` 只是把 `createV21Compactor` **暴露**给 `v21.compactionStore`（注释原话「只暴露不调用」）。在压缩真正接线并生效之前，超长会话会撞模型上下文上限 —— 表现是 `context_length_exceeded` 一类失败，而不是静默丢历史。这是本修复**有意换来**的取舍：宁可任务失败并留痕，也不静默断掉上下文。
2. **运行时的 `session/attach` 失败仍会换会话**：`runtime/turn-driver.ts` 在宿主不提供 `sessionAttach` 或会话已被清理时降级新建并标 `sessionReset`。这不是策略性轮换（compose 侧已无此路），属运行时兜底，无法在装配层避免；`persistAgentSessionAfterRun` 仍会为它记一条 info 日志。
3. **旧库里的存量数据**：`agent_sessions.turns >= 30` 或 `started_at` 很旧的行不再触发任何动作，直接继续复用（符合需求）；没有迁移脚本需要写。
4. **非 agent 任务不受影响**：`/review-pr`、`@answer` 仍是 `ephemeral`，每轮自己 create → run → archive 自己的临时会话，不涉及 issue→会话映射。
5. 端到端只在「首轮」跑了真库路径；「第 31 轮仍复用」由纯函数用例覆盖，没有花成本在真库里造 31 轮。
