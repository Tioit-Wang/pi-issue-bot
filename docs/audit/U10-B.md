# U10-B 反证核查（对另一位核查员的 4 条结论做证伪）

范围：仅 `docs/requirements.html` 行 1779-1841 的 BR-4 / BR-3 / BR-6 / BR-11。只读。

## 主张 1：BR-4「增量投喂」与需求冲突 —— **维持原结论**

- 事件消息模板把整篇正文内联，且 `edited` 与 `opened` 用同一个 `{body}`：`apps/server/src/agent/message.ts:53-69`（edited 模板 60-61 行）、渲染入口 `:270-281`（`body: renderBody(issue.body)` 无条件）。
- 阶段提示词默认模板逐条含 `{{issue.content}}`：`packages/contract/src/settings-v21.ts:487,502,515,528,546`；渲染 `apps/server/src/prompt/render.ts:148-149` 无任何条件分支。
- 「首轮/后续」判据全仓不存在：在 `apps/server/src/agent/*.ts`、`prompt/*.ts`、`app/worker-deps.ts` 搜 `first|首轮|首事件|增量|delta|hasDelivered` 零命中。
- `issues.edited` 的 `payload.changes` **只用于触发判定**，不进渲染：`http/webhook-v21.ts:129-138`（`changedFields`）→ `trigger/decide.ts:106-107,147`；全仓 `changedFields` 仅这三处。
- 一句话：没有任何「已有历史消息就省略正文」的代码，每个事件都是整篇重投。

## 主张 2：BR-3「上一轮失败的不算重复」未实现 —— **维持原结论**

- 幂等键 = 主键 `(repo, issue_number, fingerprint)`，插入语句**不看 status**：`apps/server/src/agent/store.ts:95-98`（`ON CONFLICT (...) DO NOTHING`），注释 `:206-210` 明确「inserted=false 就是同一句话已经来过 → 返回 duplicate」。
- 无「删除失败行」路径：全仓 `DELETE FROM` 只在 `jobs/metrics-rollup.ts:156`、`jobs/retention-cleanup.ts:55,74`、`skills/store.ts:640-641`，都不碰 `agent_messages`。
- 状态回滚只有注释，没有 `queued` 调用点：`markMessage`（`store.ts:278-291`，注释提到「`queued` 回滚用」）只被 `agent/dispatcher.ts:136`（置 `failed`）与 `:201`（`finishMessageAndContinue`，只允许 `done`/`failed`，见 `:198`）调用。
- 判重也不按 status 过滤：`agent/store.ts:99-101`（`readMessage`）无 status 条件，`claimOldest` 的 status 过滤只影响领取、不影响重投判定。
- 一句话：失败消息仍占主键，同内容（同 fingerprint）重投必被判 duplicate，不存在失败→queued 的回滚。

## 主张 3：BR-6「可在后台查询」未实现 —— **维持原结论**

- `decision_reason` 全仓仅 5 处命中，全是**写入侧**（或注释说明写）：`apps/server/src/db/schema.ts:124`（列定义）、`http/webhook-v21.ts:182-184,200`（UPDATE 写）、`http/webhook.ts:103,985,1016`（注释 + 写）、`trigger/decide.ts:7,30`（注释）、`trigger/roles.ts:66`（注释）。
- `queries/` 里出现的 `decision` 全是审批判定，不是 webhook 判定：`queries/audit.ts:10,107-110,247-248`（`kind='approval'` 事件 payload）。
- 契约无对应字段/端点：`packages/contract/src/api.ts` 只有 `deliveries` 计数（`:79`、`overview.ts:77`）与注释提到 `webhook_deliveries`，无 `decision*` 字段；面板 `apps/panel/src/**` 的 `decision` 只来自审批事件（`routes/task-detail.tsx:198,216-217`、`routes/audit.tsx:505-506`）。
- 反向证据还更糟：`webhook_deliveries` 本身会被保留期清理（`jobs/retention-cleanup.ts:74`），判定留痕连原始行都不保证长期可查。
- 一句话：`decision/decision_reason` 只写不读，面板与契约都没有查询面。

## 主张 4：BR-11「人工删除不构成永久否决」实现反了 —— **维持原结论**

- human-veto = 「该标签最后一次记录 `removed_at` 非空」：`apps/server/src/workflows/normalize.ts:241-263`（`humanVetoedFrom`，259 行判定），并在归一化里直接挡住重打：`:212-226`（`reason: 'human-veto'`）。
- `removed_at` 的唯一写入方就是**我们自己的成功撤标**：`workflows/bot-labels.ts:27-29`（SQL）、`:134-144`（`recordRemoved`）← `github/executor.ts:341-347`（`executeLabelPlan` 现在删成功后才记账），全仓无第二个 `UPDATE ... removed_at` 写入点（其余命中都是 `removed_at is null` 过滤或历史读取）。
- 没有 `issues.unlabeled` 记账：全仓 `unlabeled` 只命中 `github/octokit.ts:807`（我们自己撤标时调用的写动作分支）与 `jobs/reconcile-reverts.ts:5`（注释）；事件路由只映射 `labeled`（`http/webhook-v21.ts:99-100`），无 `unlabeled` 分支。
- 无清除/过期机制：唯一「解除」是出现更晚的 `removed_at IS NULL` 行（`normalize.ts:251-255` 取最新），而该行只能由我们重新打标产生 —— 而重打又被 veto 挡住（`:212-226`），死锁。
- 一句话：veto 的证据链只来自我们自己的删除动作，所以「我们自己的删除构成永久否决」，与 BR-11 相反。
