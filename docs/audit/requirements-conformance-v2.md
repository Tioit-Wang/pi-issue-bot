## 三、必须优先修的 11 项（按严重度）

### P0-1 会话会被自动归档，违反「会话常驻」
- **证据**：`apps/server/src/app/compose.ts:209-212`（`AGENT_SESSION_POLICY = { maxTurns: 30, maxAgeDays: 7 }`）、`:455-463`（命中即不带 `sessionId`，返回 `archiveSessionId`）、`:1459-1464`（生产队列 `onTaskJob` **不传 `sessionEvent`**，使 `:1315` 的「不归档」守卫失效）
- **影响**：FR-3.4、BR-「会话无结束状态」、Q-3、AC-1 不成立。7 天后上下文被强制切断。（**注意**：AC-23 的「沙箱回收/重开复用」经 CROSS 核实为**已实现**，不受此条影响——沙箱侧确有 `destroyContainer` 与重建路径，问题只在会话被换掉。）
- **裁决**：CHECK-1 采信 B（部分实现），CHECK-2 独立核实同一路径，CROSS-1 补充确认。

### P0-2 上次失败的消息被永久判重
- **证据**：`apps/server/src/agent/store.ts:95-98`（`ON CONFLICT DO NOTHING` 不看 status）、`:99-101`（读消息无 status 条件）、`migrations/0006_agent.sql:46`（普通索引，无部分唯一索引）
- **影响**：FR-3.5「上次失败不参与去重」、BR-3、AC-20 全部不成立。一次超时就会把该内容永久锁死。
- **裁决**：CHECK-1 与 CHECK-2 均独立确认，CHECK-4 核实 AC-20 不成立且与 AC-19 构成联动矛盾。

### P0-3 内容级去重口径越界
- **证据**：`apps/server/src/agent/canonical-text.ts:30-36` —— 抹代码区、删标点符号、压换行
- **影响**：需求明写「只去首尾空白、合并连续空行，不做语义近似」。实现把「措辞不同就是不同内容」变成「去标点就算同一内容」，且被测试固化。

### P0-4 增量投喂完全未实现
- **证据**：`packages/contract/src/settings-v21.ts:485-517` 五个默认事件模板全部含 `{{issue.content}}`；`payload.changes` 只用于触发判定（`trigger/decide.ts:106-107,147`），渲染阶段丢弃
- **影响**：FR-4.2、BR-4、SB-4。每个事件都重发整篇正文，与「只发变更」直接冲突。

### P0-5 上下文压缩引擎是死代码
- **证据**：`compact/` 六个文件算法完整（六阶降级、2000/500 分层、空摘要判失败、孤儿剔除齐备，79 例单测全绿），但 `compactSession()` **零生产调用方**；`compose.ts:879-881`、`worker-deps.ts:1022-1032` 两处注释自认「只暴露不调用」
- **影响**：FR-5.6 全部子项在运行期不成立；AC-24、AC-25 不具备。

### P0-6 标签删除权与删除留痕双重失效
- **证据**：`compose.ts:857-864`、`:1651-1678`（`current`/`botLabels` 取自自家 `bot_labels` 台账而非 issue 实际标签）；`db/schema.ts:381-406`（无 `removed_by`/`removed_reason` 列）
- **影响**：FR-5.4「删除人手动打的标签」永不成立；`deletionOwner` 恒为 `bot`；BR-10 删除留痕退化为自由文本。

### P0-7 BR-11 实现方向相反
- **证据**：`workflows/normalize.ts:241-263`（`humanVetoedFrom` 用「最后一次 `removed_at` 非空」判 veto）、`:212-226`（挡住重打）；而 `removed_at` 唯一写入方是 `bot-labels.ts:134-144` ← `github/executor.ts:341-347`，即**我们自己的成功撤标**
- **影响**：实际效果是「我们自己的删除构成永久否决」，与「人工删除不构成永久否决」相反；且真正的 `issues.unlabeled` 人工删除从未被接收（事件路由只映射 `labeled`）。

### P0-8 日配额完全未实现
- **证据**：`db/schema.ts:634`（`quota_counters` 表无任何读写方）、`trigger/decide.ts:251`（`dailyQuotaExceeded` 分支存在但 `decideV21Delivery` 三个调用点均不传值）
- **影响**：SL-3、FR-2.2 相关配置为死字段；「触顶拒绝并记录原因可查」完全不成立。

### P0-9 面板整体未按 §5.7 落地
- **证据**：`apps/panel/src/routes.tsx:55-59` 与 `layout/nav.ts:22-28` —— 需求点名要删的总览/成本/质量/审计/系统五个页面**全部在册且 `nav: true`**
- **影响**：FR-7.1 直接冲突；FR-7.2/7.3/7.4 缺失项多数是**契约层缺字段**（原文卡、系统提示词、token/单价、verdict/actions、写回行），不是一轮前端改造能补的。

## 六、CROSS 阶段新发现的问题（CHECK 遗漏）

### P0-10 台账漂移导致「该加的不加」
- **证据**：`apps/server/src/writeback/v21/labels.ts:183`（`add = desired − current`）、`apps/server/src/app/compose.ts:1658-1673`（`readAppliedLabels` 只查 `bot_labels`）
- **影响**：当 GitHub 上的标签被人工删掉、台账仍记 `applied`（`removed_at is null`）时，模型要求该标签 → 已在 `current` 里 → **永不补加**。删除方向安全（人标签不被删，符合 I4），但新增方向不安全。
- **来源**：CROSS-2 推翻 CHECK-1 对 SA-6 的「已实现」判定。

### P0-11 非 v2 产出仍会触发平台自决的兜底评论
- **证据链（已逐环节验证）**：
  1. `apps/server/src/worker/run-task.ts:1036` — `lastProbe = taskSource === 'agent' ? probeV21Output(captured) : { kind: 'not-v21' }`，**非 `agent` 来源恒 `not-v21`**
  2. `:1168-1174` — `v21Handled = true` 只在 `probe.kind === 'valid'` 与 `'rejected'` 两个分支，`not-v21` 不置真
  3. `:1191-1193` — `not-v21` 落到 `else` 分支，`prepared = prepareEnvelope(...)`，此时 `prepared.valid` 由旧信封决定
  4. `:1243` — `if (!v21Handled && prepared !== null && (!prepared.valid || !hasCommentAction))` 守卫成立
- **但有一条前置挡板**：`:1249` 的 `if (dryRun)` 会先把兜底评论拦成 `blocked`（`dry-run：兜底评论同样不写`）。而 `apps/server/src/app/compose.ts:1123` 的 `dryRun = input.dryRun === true || config.dryRun || policy.dryRun`，`config.dryRun` 默认 **true**（`app/config.ts:115`）。
- **准确结论**：**在关闭 dry-run 的部署上**，`not-v21` 产出会真实发出平台自决的兜底评论，与 FR-5.1「平台不预设动作」冲突；默认 dry-run 下被挡。判 **部分实现** 成立，但不是「必然发生」，是「dry-run 关闭后必然发生」。
- **来源**：CROSS-2 推翻 CHECK-2 对 P4-4 的「已实现」判定；编排侧已复核全部 4 个环节 + dry-run 挡板。
