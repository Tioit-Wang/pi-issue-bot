面板 UI 改版需求

从「五个全局页 + 只读详情」收敛成「三个项目页 + 一条会话流」。版本递进，每版能单独验收。

状态：v0.1–v0.5 已在原型 design-refactor/e-unified.html 里做出来；v0.6 只有规格，没有实现。 视觉规范见 design-refactor/assets/base.css；对话语义对齐 docs/requirements.html §5.6。

贯穿所有版本的约束（不随版本变）：
  • 外部文本（issue 正文、评论、仓库文件、模型输出）永远是数据；进提示词前必须经围栏中和。
  • 面板不假装成功：没有写接口的动作只画禁用按钮，并在 title 里写明缺哪个接口。
  • 令牌与模型 key 只在宿主进程使用，加密存储，不进容器。
  • 状态只允许小面积出现（点、chip、2px 边条），禁止整行整卡染色。

v0.1基线 · 现状

现在的面板：左栏两级导航（全局 5 项 + 仓库 5 项），顶栏 + 内容区；/ 总览、/costs、 /quality、/audit、/system 各自成页；issue 详情是一堆只读分区（概况 / 会话 / 动作 / 事件）。

问题表现
导航与内容同权左栏吃掉 15% 宽度，五个全局页一天只被打开几次
issue 页不是「对话」把会话、动作、审计拼成卡片，人要在四块里找「它现在卡在哪」
只读红线「重跑」「暂停全部」是禁用按钮，面板无法推动任何事
模型配置无处安放只有项目级「默认模型」一个下拉，供应商 / key / 单价没有地方看

v0.2结构收敛 · 原型已实现

把「三层」压成三层，但每层只留一个入口。

层内容位置
项目上下文acme/widgets · other/lib · 全部项目左上角下拉；切换时列表、计数、设置页标题一起变
项目级导航Issue · 设置 · 技能底部 dock（三项）
全局系统状态 / 运行时 / 供应商与模型 / GitHub 身份 / 连接 / 只读常量dock 最右「系统」→ 模态框

被删的页面与去处

原页面去处
总览四个关键数字进顶栏状态带（待处理 / 运行中 / 失败 / p95）+ 一个降级 chip
系统doctor 五项检查、运行时开关、连接、只读常量进「系统」模态框
成本金额作为单次运行的元信息（12.4k tok、单价），不再有独立页
质量（被改回）并入审计事件，审计本身也不单独成页
审计写回行直接出现在会话流里（✓ 写回 标签 + 评论 slot=… · 2/2 成功）
验收口径：删掉的每一条信息，必须在上面某处能找到；找不到就不许删。以后若发现「还是有人天天看」， 先往状态带加数字，再考虑加回页面——顺序反过来成本高得多。

v0.3左栏统一 · 原型已实现

Issue 队列 / 设置分区 / 技能列表原来分别是 340 / 184 / 300 宽，头部有三种画法，选中态有三种画法。

  • 宽度收成一个数 320，不设例外（窄屏 1100px 以下统一降到 300）。
  • 头部统一为 .rail-head：30px 高、10px 大写小标 + 右侧计数，1px 底边。
  • 行高 28；hover 是 --surface-2；选中统一「左侧 3px accent 条 + accent-soft 底」。
  • 字号：行 12px / 12.5px，次行 10.5px，等宽只给 ID、路径、标签键。
为什么不让队列去迁就另两栏的窄宽：队列是主工作区，它的两行文字（标题 + 原因）决定了下限； 另两栏是一行条目，宽到 320 只是多留白，不会更难用。统一方向要朝信息量大的那一侧。

v0.4Issue 页 = 会话流 · 原型已实现

点进一条 issue，看到的是一条完整会话，而不是分区卡片。骨架按 docs/requirements.html §5.6 的示例： 「消息行无卡片、工具调用是弱化的折叠行、只有用户输入才有气泡」，再加后台特有的三样东西（系统提示词、 每条输入的事件元信息、平台写回结果）。

从上到下

  1. 常驻一行标题：#318 · Promote 按钮… · blocked · ⋯。`⋯` 里放重跑 / 标记人工 / 在 GitHub 打开。
  2. Issue 原文卡（折叠，默认收起）：收起时只有标题一行 + 原文 · @dana · 4 条评论； 展开是作者、时间、标签、正文。评论不进这张卡——它们按时间进入下面的会话流，避免同一句话在一个屏幕上出现两次。
  3. 系统提示词（居中、可折叠、不可删）：系统提示词 · 项目级 · 每次调用都带 · 不参与压缩 · 4.1k tok。 展开就是那段 markdown 文本本身（等宽、保留换行、最多 300px 高后内部滚动）， 因为要回答的是「发给模型的到底是什么」。只放一块，不在每条回复前重复； 每条 agent 轮次的行内标签（model claude-x · 12.4k tok）承担「它确实带了」的证据。
  4. 人 / 触发 → agent 的输入（右侧气泡）：气泡上方是触发来源 chip（issues.opened / issue_comment · @pi / /recheck），下方是等宽事件行（issues.opened · #318 · 2026-05-31T08:24:11Z）。 这一行是「它为什么跑了」的唯一解释，不许省。
  5. agent（左侧，无卡片）：agent · 08:31 · run 4a11c2 · 5.2s + 最终回答， 下面是三层工具（轮 → 组 → 工具行：名称 / 参数摘要 / 结果 / 耗时，失败行红点）， 再下面是默认收起的 verdict/actions JSON（标签写「声明了 N 个动作」）， 最后是 chips（模型 / token / 运行中）。
  6. 平台写回（居中细行，不可折叠）：✓ 08:32 写回 标签 needs-info + 评论 slot=format-review · 2/2 成功； 失败换红 ✕。它回答的是「实际做了什么」，与上面 JSON 的「声明了什么」必须能分开看。
  7. 输入区：身份 chip（@dana（你的账号） 或 bot）+「会 @ 上 agent」+ 预览态禁用发送按钮。
本版明确不做：发送。输入框只出 UI，按钮 disabled，title 写明缺 POST /api/issues/:owner/:name/:number/messages。原因见 v0.6。

验收

  • 1440×900 下，一条有 3 轮的 issue 首屏能看到：标题行、原文卡（收起）、系统提示词（收起）、 第一条人类输入、第一条 agent 回答的前两行。
  • j/k 切条目时，会话区滚回顶部；Esc 收 ⋯ 菜单。
  • 把系统提示词块展开，看到的是完整 markdown（# 角色 / ## 硬约束 / ## 证据要求 / ## 本轮的产出 四节）， 不是分层表格。

v0.5全局模型与身份 · 原型已实现

「系统」模态框新增两块，排在系统状态之前（模型配置是这一屏的主任务）。

供应商

字段说明
名称 / base URL / key（掩码）/ 连通性 / model一条一行。key 只显示后三位与「已存 / 未配置」；连通性是状态点 + 延迟，可「测试全部」（原型禁用）
OpenAI 兼容端点自建网关按同一行填写，model 里标注「OpenAI 兼容端点」，不另开一套表单

模型角色

角色用途单价 in / out
agent 执行跑 issue 的正式轮次$3 / $15
format 快速格式检查、短分类$0.8 / $4
classify 分类标签判定（要 path:line 证据的那种）$0.4 / $1.2
兜底主模型 429 / 超时后降级$2.5 / $10
单价为什么必须在这一屏：成本页已经在 v0.2 删掉了，单价是界面上唯一能解释 「这次为什么花了 $0.112」的依据。没有单价，成本就只剩一个不可解释的数字。

GitHub 身份

  • 默认 bot · gh-bot[bot]；填了个人令牌就用你的账号发评论（需要 issues: write）。
  • 取法用手动 PAT，不做 OAuth device flow：后者要注册 OAuth App、多一个换发 token 的端点， 收益不抵成本。补一个「检查权限」按钮校验 scope 与过期时间即可。
  • 令牌加密存储、只在宿主进程用、不进容器；解不开要报错，不许静默当成「没有令牌」。
与项目级的关系：全局是默认值；设置 → 执行 那行改成「默认模型：继承全局（claude-x）>」， 点开才覆盖。两处都能直接选模型，一定打架。

v0.6面板发送（未实现，只有规格） · 需新接口

目标：在会话流底部回复，这条回复同步到 issue 评论，agent 的回复也回到这里。 现在没有任何写接口能承载它——http/api/ 下 12 条只读 GET + 10 条配置类写 （repo settings、skills），评论必须回 GitHub 提，再由 issue_comment.created + @别名 回流。 所以这一版要先加接口，再加 UI 的 disabled 开关。

接口草案

POST /api/issues/:owner/:name/:number/messages
Header: X-Pi-Bot-CSRF: 1        // 与技能写面同一套 writeGuard
Body:   { "body": "…", "wake": true }
200:    { "commentId": 1952884, "messageId": "am_7f3c1a", "queued": true }
409:    { "error": "writeback-disabled" }   // 该仓库写回闸门关闭
403:    { "error": "forbidden" }            // CSRF / Origin / PI_BOT_PANEL_WRITE=off

服务端要做的事（顺序不能换）

  1. 契约：packages/contract/src/api.ts 加请求/响应 schema；schemas.ts 注册表只许加名字。
  2. 写入：用面板配置的身份（个人 PAT 优先，否则 bot）在 issue 上代发一条评论，正文末尾按需追加 @别名。
  3. 落库：同一事务里往 agent_messages 插一条（kind: 'panel'，comment_body = 正文）， 并把 actorLogin 记成发起的操作者。
  4. 入队：wake: true 时立刻入队；不等 webhook 回流（自己发的评论不一定回给自己，回流不可靠）。
  5. 错误：新增错误码要同时动契约 ErrorCode、http/errors.ts 映射、面板 describeError。

安全

  • 走 writeGuard：X-Pi-Bot-CSRF: 1 + Origin 校验 + PI_BOT_PANEL_WRITE=off 时 403。
  • 正文必须当外部文本处理：进提示词前经 skills/prompt.ts 的围栏与蒙版，不许拼接指令。
  • 个人令牌只在宿主进程解密使用；容器内只看得到围栏后的文本。

验收

  • 面板里发一句 → issue 上出现一条评论（署名正确）→ 会话流里出现对应 human 行（via 面板 标记）→ 一轮结束后出现 agent 回答与写回行，且 issue 评论被同一 slot 覆盖而不是新增。
  • 未配置个人令牌时署名是 bot；配置了但不能用（scope 不足）时，发送按钮上方给出明确失败原因，而不是静默成功。
  • dry-run 打开时：只写本地 actions 记录，issue 上不出现评论，会话流里的 human 行标 dry-run。
