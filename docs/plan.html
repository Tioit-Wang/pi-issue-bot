用 PI SDK 做一个
Issue / PR 自动处理平台

打标、合规检查、@机器人 /命令、自动建 issue、自动推分支开 PR——全部自动，不设信心阈值，也没有合并权。 这套系统真正的边界不在「能做多少」，而在不可信代码在哪跑、钥匙放在哪。

核心判断 沙箱里只装不可信的东西。agent 是拿着钥匙的一方，它不进容器；容器里没有凭证，也就没有值得偷的东西。

01

已确认约束

两轮讨论定下的九条，后面的设计不超出这个范围。

D1部署形态单组织自托管，一个 GitHub Org、少量仓库，单机
D2代码托管GitHub.com，用 GitHub App：安装级 token、1 小时过期、权限可收窄、可审计
D3写操作打标 / 评论 / 建 issue / 推 commit / 开 PR 全自动；没有合并能力
D4分析深度真实检出：clone + 装依赖 + 跑测试，每任务独立 worktree
D5沙箱Docker，一任务一容器，按结果销毁；agent 在宿主机，只有命令进容器
D6置信阈值不设。判定靠证据不靠自评分；关闭 issue 走确定性条件（见 05）
D7网络公网放行，内网与云元数据地址阻断；完全断网降级为高风险任务的加固档
D8人工取消事前审批与事后复核，只保留异常兜底通知
D9规模< 100 事件/天，2–4 并发
02

核心矛盾

D3 与 D4 组合起来就是这台机器最危险的地方：同一台主机上，既有外来代码的执行权，又有仓库的写凭证。取消阈值、全自动之后，防止误判的缓冲垫没有了，唯一还能依靠的就是「结构上做不到坏事」。

常见两种做法都不可接受：

  • 把 agent 也塞进容器——模型密钥跟着进去，陌生代码和 agent 住一间屋，结论可被篡改；
  • 不隔离、靠提示词约束——postinstall 一行脚本就能反弹 shell，提示词拦不住。

方案取第三条路：把「想」和「做」分开。agent 在门外做推理，容器只负责跑命令；凭证永不进入不可信一侧，agent 的产出还得先过结构化校验才能变成 GitHub 写操作。

03

架构与执行边界

可信侧 · 宿主机
  • 控制面验签 · 去重 · 队列 · 重试 · 熔断 · 写执行器
  • pi-host + agent-runtime推理、技能、模型请求、transcript 落 host-core
  • 凭证GitHub installation token 与模型 key 只在这一层
  • 文件工具Read / Glob / Grep / Edit 直接操作挂载目录
↕ Bash docker exec
不可信侧 · 容器
  • worktree挂载到 /work，一任务一份
  • 装依赖与跑测试执行陌生仓库的 install / test / build 脚本
  • 无凭证没有 GitHub token、没有模型 key、没有 docker socket
  • 有公网、无内网装依赖需要公网；私网段与元数据地址不可达

跨边界的只有一条通道：送进一条命令，收回一段输出。

实际执行位置

东西在哪隔离
控制面 / pi-host / agent / 凭证宿主机进程无（可信侧）
pnpm install、测试、构建、每条命令容器内namespace + cgroup + cap-drop + 只读根 fs + 非 root
仓库文件同一份 bind mount宿主直接读写，容器只见 /work
命令与会输出跨边界唯一数据通道

为什么 agent 不进容器

「沙箱就是 Docker」没错，要补的是沙箱里装什么。容器是给陌生人用的隔离房间：可以让他进去跑工具、装东西；但不会自己也搬进去住，尤其口袋里还有钥匙。

  1. 同一个进程空间。陌生代码和 agent 共处一容器，前者能读后者的环境变量（模型 key 就在里面）、能 ptrace 它、能把它杀掉。
  2. 结论可被篡改。agent 的判定决定要不要推 commit、要不要发评论；判决者和被观察者住一间屋，这个判定就不值得信。
  3. 工程代价。镜像从约 400 MB 涨到 1.5 GB+（要装 pi-host 与运行时打包）；transcript 由 Rust host-core 独占写入，塞进一次性容器就得每任务一个库，或者把权威数据库挂进不可信环境——后者更糟。

如果坚持让 agent 进容器，代价是：需要一个能注入模型 key 的宿主侧出口代理、接受每任务独立 transcript 库、并放弃「结论不可被篡改」这个性质。技术上能做，不划算。

任务信封

agent 拿不到 GitHub 凭证，只能交出一份结构化结果，由控制面校验后决定执行哪些动作。字段不合规的动作直接丢弃并记为解析失败，没有自由发挥的通道。这条约束不因 agent 在哪而改变——它防的是「被 stdout 里的陌生文本说动」。

// 每个任务结束时 agent 只能交出这个
{
  "verdict": { kind:"issue", labels:["bug"] },
  "actions": [
    { intent:"comment",     body:"…" },
    { intent:"label",       add:["bug"] },
    { intent:"create_issue", title:"…", fingerprint:"dep-vuln:x" },
    { intent:"push_branch",  branch:"bot/fix-123", openPr:true }
  ],
  "usage": { inputTokens:0, outputTokens:0, costUsd:0 }
}

信封里故意没有 confidence：自评分不可核查、没有消费方，而且最容易被顺手改回阈值。可核查的是证据——每条判定附命中的规则与原文片段（见 04.2）。

04

能力清单

04.1

分类打标issues.opened / edited / reopened

  • 标签来自仓库的 .github/pi-bot.yml，不发明新标签；默认集 bug / feature / question / docs / needs-info / area/*
  • 不设信心阈值：一律打标；判定附命中的规则与原文证据，不用自评分
  • 幂等重算：issue 被编辑后重判，只增删自己打过的标签，人打的不动

敢全自动不是因为判断准，而是因为可逆：标签可撤、评论可改、commit 只落在 bot/* 分支。可逆性替代了阈值。

04.2

标准合规检查与自动回复合规闸门

  • 规则来源：issue 模板必填项 + 配置里的显式检查（复现步骤、版本号、日志）
  • 判定结构化：每条规则 pass/fail 附 issue 原文证据，不是客套话
  • 不合规 → 一条评论列出缺什么、附模板片段，打 needs-info
  • 只在缺失项集合变化时再回复；同一句话不催第二次

阈值取消后，噪音控制只剩下这一条。机器人最大的敌人不是判错，是被当成刷屏。

04.3

主动建 issue新增能力

  • 触发场景：PR review 顺带发现的独立缺陷、依赖与回归告警；同类 issue 汇总默认关闭
  • 去重键 (repo, 指纹)：命中就追加一条评论到原 issue，不新开
  • 日配额默认 10 个/仓库，超限写入待办队列而不创建
  • 只创建、不关闭；关闭属于不可逆动作，走 04.2 的条件闸门

这是唯一一种「不可逆的噪音」：开出去的 issue 会通知全组。所以它单独有配额和去重，不受「无阈值」影响。

04.4

@ 触发的技能指令/review-pr · /issue-triage · /issue-repro

  • 门禁看 author_association：OWNER / MEMBER / COLLABORATOR 或白名单；机器人账号忽略
  • 命令即技能（markdown frontmatter），仓库可自带技能，与内置命令同级
  • 同一 head_sha 重跑是空操作；换了新提交则取代上一条评论
  • 10 秒内给出回应（表情或一行确认），否则用户以为没生效

技能是唯一需要写代码的地方，其余都是配置——维护者能自己加命令而不动平台。

04.5

Web 统计面板唯一的质量信号

  • 吞吐：事件量、任务结果分布（成功/失败/超时/熔断/解析失败）、p50–p95 耗时、队列深度
  • 自动执行后被人改回的次数与比例——事后复核取消后，这是唯一的质量指标
  • 成本：按仓库/命令拆的 token 与金额，最贵的十个任务
  • 审计：谁触发的、跑了哪个提交、写了什么，可导出

面板不做事前拦截，只做事后可见。看得见，才敢继续放开。

05

权限与闸门

能自动的全部自动，剩下的不是「人工审批」，而是零成本的机器约束。

打标签
自动
无阈值；只增删自己打过的
发评论
自动
结构化校验通过 + 隐藏任务标记 + 频率限制
创建 issue
自动
去重键命中则追加评论；日配额 10/仓库
推 commit / 开 PR
自动
只到 bot/* 分支；永不强推，永不改写贡献者分支
关闭 issue
有条件
不在全自动清单内：带 needs-info + 缺失项 48h 未变 + 无人回复（确定性条件，不看自评分）
合并
不存在
代码层不实现 merge 调用；分支保护强制人工 review 兜底
「没有合并权限」要落到哪里

GitHub 的权限粒度到不了「能推 commit 但不能合并」这一档——merge 和推 commit 共用 Contents: write。所以是双保险，不是单点：

  1. 代码层面不存在 merge 调用，App 清单里也不勾选相关能力；
  2. 受保护分支要求人工 review 与必需检查全绿——这是真约束，任何人都绕不过；
  3. 每次写操作进审计，与 GitHub 侧审计对账。
权限全给的对应措施

installation token 本身 1 小时过期、只作用域到配置的仓库、只存在控制面进程里、每次写操作留痕。这样即使 agent 被注入，损失上限是「一个仓库、一小时内」，而不是「整个组织」。

06

沙箱与网络

一任务一容器，常驻空闲进程，按需 exec。参数写死，不留给调用方决定。

docker run -d --init --rm \
  --name pi-job-<id> \
  --user 1001:1001 \
  --read-only --tmpfs /tmp:rw,size=512m,noexec,nosuid \
  --cap-drop ALL --security-opt no-new-privileges \
  --pids-limit 512 --memory 2g --memory-swap 2g --cpus 2 \
  --ulimit nofile=4096 \
  -v /srv/pi/jobs/<id>/work:/work:rw \
  -v pi-dep-cache:/cache:ro \
  -w /work \
  pi-worker:<toolchain> sleep infinity

网络策略

不强制断网——装依赖本来就要公网。容器里没有任何可偷的凭证，所以外传本身不是威胁；真正的威胁是把它当跳板去扫内网、打云元数据。所以按「能不能去哪」来切，而不是按「有没有网」。

放行
公网
包管理器仓库、公共 CDN 等一切正常出网需求
阻断
私网与元数据
10/8 · 172.16/12 · 192.168/16 · 169.254/16 · ::1
可选加固
完全断网
高风险任务（会自动推分支的）可切到 --network=none

实现两条路，按环境选：出口代理 + allowlist（可控，需一个代理进程）或 docker network + iptables DROP 私网段（零依赖，够用）。两条都要覆盖 IPv6。

容器生命周期

不定销毁策略，磁盘会被调试残留吃干净。--rm 只是兜底，真正的清理靠这张表。

结果容器worktree
成功立即销毁保留 24h 供查 diff，之后回收
失败（非超时）保留 1h 可复现，之后强删保留 1h
超时 / 熔断立即 SIGKILL立即回收
磁盘水位 > 85%强制清理最旧的失败容器无视保留期，清最旧

四条不可让步的红线

  • docker socket 只挂控制面。socket 等价于宿主机 root，进容器等于把逃逸入口递进去；
  • 容器里没有任何 token，模型请求由宿主代发，容器连 key 的影子都看不到；
  • 能力全砍：cap-drop ALL、只读根文件系统、非 root、pids 与内存上限；
  • 挂载只给一份 worktree，不给宿主目录、不给数据目录。

预检：不通过就拒绝启动

daemon 可达 · 磁盘 ≥ 20GB · worker 镜像存在且工具链匹配 · 金丝雀容器里访问 169.254.169.254 确实失败 · --memory / --cpus 真的在生效。最后一条最容易被忽略：Docker Desktop 里 cgroup 有时不落地，静默跑成无限制比报错危险得多。

验证边界

当前这台开发机没有 Docker，也没有 WSL 发行版。容器行为只能在目标机或 CI 上验证——本地的绿灯不能当成沙箱可用。Windows 侧还有两个限制：挂载 Windows 路径走 9p/virtiofs，装依赖慢 2–4 倍；所有容器共享 Docker Desktop 的 Linux VM，隔离上限是 Windows ← VM ← 容器，单组织自托管够用，但不是多租户边界。

07

时间、重试与熔断

全自动之后，失败处理就是全部运维。这一节的目的只有一个：别让一次事故变成一张账单。

三层时间闸

层级默认超时处置
单条命令120s（install/build 类放宽到 300s）杀掉该条命令，记 command-timeout，让 agent 决定换策略
单任务20min（/review-pr 30min）kill 容器 + 中断轮次，记 timed-out
队列等待10min回复「排队过长，请稍后」，不占并发

超时的任务不自动重试——重试只会再烧一遍同样的时间与 token。只接受人工 /retry。

重试矩阵

错误重试做法
429 限流是优先读 retry-after，否则指数退避 + 抖动，最多 4 次
5xx / 网络抖动是同上，最多 3 次
容器崩溃最多 1 次第二次仍崩判为环境问题，转异常兜底
401 / 403 / 其他 4xx否转异常兜底
结果解析失败否重试会得到同样的坏输出，需调 prompt
命令级超时否记为失败，交给 agent 换策略

两条硬约束：非幂等写不盲目重试——评论、打标、建 issue 重试前先查现状，靠隐藏标记与去重键兜住；连续 5 次 429 触发全局熔断 15 分钟，避免把配额一次打穿。

重复输出熔断

AI 卡在同一个思路里反复说同一段话时，表现不是「慢」，是按 token 计费的无限循环；而且重复推理往往意味着上下文已经被污染，重试只会把同样的坑再走一遍。所以这一条与限流熔断并列，属于硬保险。

触发条件（满足任一即中止本轮）
  1. 段落重复：归一化（去空白、去标点）后，同一段 ≥ 200 字符的窗口在一次任务里出现 ≥ 3 次；
  2. 低增量：最近 4k 输出 token 里新增 n-gram 占比 < 5%，等于在自我复述；
  3. 工具循环：同一工具、同一参数连续调用 3 次，且没有产生新的文件或测试结果变化。

处置：turn/interrupt 打断本轮 → 任务标 degenerate-output → 不自动重试 → 已产出的结构化结果照样校验入库（能救回多少算多少）→ 进异常兜底通知。

异常兜底

这是唯一保留的人工触点，且只在失败时出现：超时、熔断、认证失败、解析失败、容器崩溃。正常路径完全静默——没有「请审批」，只有「出事了」。

08

里程碑

每一阶段都以「仓库开关 + dry-run」交付，dry-run 永久保留。

  1. M0
    最小闭环
    GitHub App、webhook 验签与去重、任务表、拉起 pi-host 跑一个写死的技能，只产出不写入。目标是把端到端链路跑通，不带任何智能。
  2. M1
    分类与合规（含首周观察期）
    04.1、04.2、标签与评论执行器、只读任务的容器档。上线首周强制 dry-run：照常判定、不写回，用真实 issue 回放校准 prompt。观察期不是审批，是校准。
  3. M2
    命令面与运行时保险
    04.4 的命令注册表与鉴权、10 秒应答；/review-pr 接真实检出与测试执行；同批交付三层超时、重试矩阵、重复输出熔断——它们不是后续优化，是 M2 的验收项。
  4. M3
    面板与主动建 issue
    04.5 的只读视图与审计日志、04.3 的去重与配额；含「自动执行后被人改回」的采集口径。
  5. M4
    写回升级
    默认 auto 的 push_branch + 开 PR；不合规关闭走条件闸门。合并不实现。
