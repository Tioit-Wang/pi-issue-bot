Issue 处理平台 · 需求文档

以「一个 issue 一个会话」为核心，把 GitHub 上散落的事件收敛成可追溯的一次协作过程。

L0 功能范围

它解决什么：issue 从创建到关闭会产生很多事件——新建、编辑、打标、评论、关闭。现在每来一个事件就当作一次独立任务，agent 每次从零开始，正文重复注入，结论互不相认，事后也拼不出一条完整的处理链路。

它怎么做：平台接收 GitHub 的 webhook，按项目级配置判断这个事件要不要触发、用哪套提示词模板；触发的进入这个 issue 唯一的 agent 会话，由平台负责排队与协调；agent 的工具调用、token 消耗、完整对话全部落库，后台一处可查。

1背景与问题

本章说明为什么需要这个平台，以及不做会怎样。

仓库的 issue 是需求、缺陷、讨论的天然聚合点。一个 issue 从提出到关闭，通常经历这样一串动作：

阶段GitHub 事件人的真实动作
提出issues.opened写正文、贴日志、选模板
补充issues.edited / 评论补环境、补复现步骤、回答提问
分类issues.labeled维护者打上类型与优先级
跟进issue_comment.created@机器人 问一句、要求重跑
收尾issues.closed确认修复、关闭

这些事件在 GitHub 侧是同一个 issue 的不同阶段，但在处理侧如果被当成互不相干的任务，会带来三个具体问题：

问题表现后果
上下文断裂 第二次处理时 agent 不知道第一次已经判过什么、说过什么 结论互相打架，甚至推翻自己上一轮的判断
重复注入 每个事件都把完整正文、背景、规则再发一遍 token 随事件数线性膨胀，成本不可控
过程不可见 只有一个"成功/失败"结果，看不到中间调了什么工具、花了多少 出问题无法定位，也无法评估该不该继续用
核心判断

issue 才是处理的基本单元，事件只是这个单元上的增量输入。平台的设计起点必须从这里开始。

2目标与非目标

本章划定做与不做，避免范围蔓延。

2.1 目标

编号目标达成标志
G-1一个 issue 只对应一个 agent 会话同一 issue 的多次处理共享 session，历史可延续
G-2事件是否触发、用哪套提示词，由配置决定改配置即可改变行为，不需要改代码
G-3全过程可查后台能看到完整对话、每次工具调用、token 消耗
G-4平台按项目分区平台级给默认，项目级可覆盖；不同仓库互不干扰

2.2 非目标

  • 不合并 PR。平台只负责产生改动与评论，合并权始终在人。
  • 不做多代码托管平台。只对接 GitHub，不考虑 GitLab、GHES。
  • 不做审批流。不设置事前审批；异常走兜底通知，不走人工卡点。
  • 不做多租户。单组织、少量仓库、单机部署。
  • 本期不处理 PR 事件。GitHub 会投递 pull_request.*，平台收到后按「未触发」处理并留痕，不做评审、不开 PR 评审会话。文档里提到的「PR 与 issue 各自独立会话」是预留边界，不是本期需求。

3角色与典型场景

本章用三个真实场景说明需求从哪来，后续功能需求都可以回溯到这里。

3.1 角色

角色关心什么在系统中的动作
提交者问题有没有被认真看提 issue、补信息、追问进展
维护者进来的东西是否合格、分类是否正确打标、要求补充、关闭
平台配置者触发规则是否符合这个仓库的习惯改项目配置、调提示词模板
平台运维者成本、稳定性、异常看后台、查会话、调并发与配额

3.2 场景 A：新 issue 进来，格式不合格

经过。提交者在仓库里开了一个 issue，正文只写了一句「导出闪退，急」。几分钟后收到一条评论，指出缺少复现环境、版本号、复现步骤，并给出模板示例；issue 被打上「需补充信息」的标签。

期望行为。平台收到 issues.opened，按项目配置判定该事件触发；用这个事件的提示词模板渲染出指令，交给这个 issue 的会话。至于「该发什么评论、该打什么标签」，由提示词对应的处理自行决定——平台不预设动作，只负责把它们执行出去。

3.3 场景 B：作者补充信息，需要复核

经过。提交者编辑正文，补上了版本、机型、复现步骤。系统不再重复一遍"请补信息"，而是针对新增内容判断是否已经足够，并把结论追加在原有评论下面。

期望行为。平台收到 issues.edited，判定正文确实变了（不是只改标题或空白），复用场景 A 建立的会话，只把变更部分与本轮指令发过去，agent 基于已有上下文给出增量结论。

3.4 场景 C：维护者在评论里追问

经过。维护者在评论区 @机器人 这条和 #1942 是同一个问题吗。平台识别到提及，进入同一会话回答，而不是新开一段对话。

期望行为。平台收到 issue_comment.created，先过评论闸门（是否提及、是否限定角色、是否已关闭），通过后进入会话；提示词模板里可使用评论正文与评论人。

共性

三个场景是同一个 issue 的三个阶段。会话必须是同一条，否则 B、C 都要重新解释一遍 A 发生过什么。

4系统边界与总体结构

本章界定两个系统各做什么，以及平台内部如何分工。

整体分为两个系统，边界清晰、职责互斥：

系统职责不做什么
GitHub 平台 产生事件；承载 issue、评论、标签、PR；接收写回 不判断该不该处理，不保存处理过程
Issue 处理平台 接收事件、判定触发、协调会话、驱动 agent、记录全过程 不合并 PR，不替代人做最终决策

4.1 平台内部四个部件

平台内部按职责分为四块，四块互有关联，但都在这一个平台之内：

四个部件在同一平台内：配置决定行为，调度串起流程，Agent 负责执行，记录负责留痕。箭头是主要关联，不代表全部调用。

边界

Agent 不直读配置，也不直连 GitHub。它只接收调度渲染好的输入，输出也只回到调度。这条边界决定了配置改动不需要动 agent。

5功能需求

本章是文档主体。每个需求给出编号、描述、规则与验收要点，编号在后续设计与测试中直接引用。

5.1 事件接入

FR-1.1接收 GitHub webhookP0

平台提供单一 HTTP 入口接收 GitHub 的投递，支持的事件类型至少包括：issues、issue_comment、pull_request、installation 系列。

  • 必须读取原始请求体，不得先做 JSON 解析（否则签名无法校验）。
  • 必须读取三个请求头：事件类型、投递 ID、签名。
验收要点：同一条真实投递重放两次，第二次不产生重复处理。
FR-1.2签名校验P0

对每个请求做 HMAC-SHA256 校验。校验失败返回 401，但仍要落库留痕，便于排查配置错误。

FR-1.3投递去重P0

以 GitHub 的投递 ID 作为唯一键。重复投递视为正常现象（GitHub 会重投），直接返回成功，不重复处理。

规则：去重必须在持久层完成，不能只在内存里去重——进程重启后内存表会丢。
FR-1.4应答时限P0

平台必须在 10 秒内返回 2xx，实际处理异步进行。超时会导致 GitHub 重投，放大负载。

5.2 事件触发配置

FR-2.1每个事件一个触发开关P0

项目配置中，每一种事件都要能单独配置「是否触发」。未配置时继承平台默认值。

事件全集与默认值：

事件平台默认说明
issues.opened触发首次处理，通常对应格式评审或分类
issues.edited触发仅正文变更时触发；只改标题或标签不触发
issues.labeled条件命中所配标签才触发
issues.closed关闭收尾语义，按需开启
issue_comment.created条件过评论闸门后才触发，见 FR-2.4 评论事件的额外闸门
pull_request.*独立属于 PR 会话域，不进入 issue 会话
FR-2.2触发时发送的提示词模板P0

每个事件除了开关，还要能配置一份提示词模板。事件触发时，平台用这份模板生成发给 agent 的指令。

  • 模板是纯文本，可包含占位符（见 FR-2.3 占位符替换）。
  • 模板按「项目 + 事件」维度配置；未配置时使用平台内置默认模板。
  • 模板中通常包含技能触发词，用于让 agent 知道该加载哪套规则。
示例模板：/issue-format-check#{{issue.number}} {{issue.url}} 正文：```{{issue.content}}```
FR-2.3占位符替换P0

模板中的占位符在发送前被替换为本次事件的实际内容。

  • 可重复出现：同一个占位符在模板里出现多次，每一处都要替换，不能只替换第一次。
  • 逐个替换：一次遍历完成全部替换，替换结果不再参与二次替换（防止内容里带占位符被误替换）。
  • 未知占位符：原样保留，不做替换（{{issue.foo}} 是什么样就发什么样），同时在后台记一条配置告警。
可用占位符：见 6.3 占位符清单。
FR-2.4评论事件的额外闸门P0

评论事件比其他事件多一层筛选，因为评论量最大、噪音最多。项目可为评论事件单独配置四个闸门：

闸门默认含义
是否提及才触发 是 评论里出现合法的提及才触发；合法规则见 FR-2.5
是否限定角色 否 只允许项目级已定义的角色触发；此处只能从角色清单里选，不能临时填写
是否忽略机器人自身 是 机器人自己发的评论不触发，避免自问自答
是否响应已关闭 issue 否 issue 关闭后的新评论默认不处理
优先级：评论闸门在事件开关之后判断。开关关闭时，闸门一律不生效。
FR-2.5提及关键词与合法提及P0

项目级配置里维护提及关键词（如机器人句柄、别名），评论闸门据此判断"是否被提及"。

合法提及必须同时满足两条：

  • 以 @ 开头，紧跟项目配置的关键词；
  • 关键词之后必须是分隔符（空格、换行或标点），再接正文内容。
判定评论内容原因
合法@pi-bot 帮我看看这条关键词后是空格，正文独立
合法@pi-bot只有提及、没有正文，也认
不合法@pi-bot帮我看看这条关键词与正文粘连，无法确定边界
不合法@pi-botx 帮我看看命中的是另一个更长的名字
注意

中文用户习惯写成 @pi-bot你好，按上面的规则不会被识别。这是为了不误伤 @pi-botx 这类名字而付出的代价——如果实际使用中漏触发严重，再考虑放宽到"关键词后紧跟中文也算"，但需要同时解决名字前缀冲突。

5.3 会话协调

FR-3.1一个 issue 只对应一个会话P0

平台维护「仓库 + issue 编号 → 会话 ID」的映射。同一 issue 的所有已触发事件，都进入这同一个会话。

  • 映射是一对一，且是唯一权威来源；其他部件不得自行推断会话归属。
  • 首次触发时创建会话；后续触发复用，不新建。
边界：PR 与 issue 各自独立会话，不共享上下文。
FR-3.2多事件进入同一会话P0

事件进入会话的方式是「追加一轮」，而不是「重开一段」。每一轮（turn）都建立在前一轮的历史之上。

为什么：场景 B 需要知道场景 A 判过什么；否则 agent 会重复提问、重复下结论。
FR-3.3同 issue 串行，跨 issue 并行P0

同一个 issue 的事件必须排队，同一时刻只允许一轮在跑；不同 issue 之间可以并行。

  • 事件到达即入队，不得因为前一轮在跑而丢弃。
  • 队列按到达顺序消费，保证处理顺序与事件顺序一致。
风险提示：并发写同一会话会导致上下文交错、产出互相覆盖，这是硬约束而非优化项。
FR-3.4会话常驻，沙箱随 issue 关闭回收P0

会话没有「结束」这个状态。issue 随时可能被重新打开，任何归档动作都会让重开的 issue 失去上下文。

  • 会话与该 issue 同生命周期：创建后一直有效，不归档、不释放映射。
  • issue 关闭时只回收 agent 沙箱（占资源的容器），会话与记录保留。
  • issue 重开时直接复用原会话，不需要重建，历史上下文仍在。
  • 运行状态只有两种：活跃（沙箱存在）/ 空闲（沙箱已回收，下次触发时重建）。
回收是资源动作，不是数据动作：记录永久保留，后台随时可查完整对话。别把「省内存」做成「丢历史」。
FR-3.5幂等：三层去重P0

同一个输入不得被消费两次。去重分三层，逐层收窄：

层去重键挡住什么
投递级GitHub 投递 ID同一条 webhook 被重投（GitHub 自动重试）
事件级事件自身唯一标识同一事件经不同路径重复投递
内容级同一 issue 内评论正文（规范化后）人手动重复 @ 两次、同一段话反复粘贴

内容级去重的口径

  • 作用域只看 issue 内：不同 issue 出现同样的话是正常现象，不能跨 issue 判重。
  • 比较规范化后的正文：去首尾空白、合并连续空行；不做语义近似判断——措辞不同就是不同内容，宁可多处理一次，也不能把新问题误判成旧问题。
  • 与作者无关：两个人贴了完全相同的日志，处理结果一样，只处理一次。
  • 上次失败不参与去重：上一轮是超时、崩溃或未产出，等同内容再来一次视为重试，必须放行。否则一次故障会把这个内容永久锁死。
  • 跳过要留痕：判定为重复时不静默丢弃，记一条「因重复内容跳过」，后台可查。
与输出侧的分工：输入侧靠内容去重（避免重复处理），输出侧靠评论槽位（避免重复发）。两者解决的是不同方向的重复，不能互相替代。

5.4 提示词下发

FR-4.1拼接结构P0

发给 agent 的提示词由四段构成，顺序固定：

序段示例作用
1技能触发词/issue-format-check决定加载哪套技能与产出格式
2issue 锚点#1950人可读的定位符，日志与评论中对照用
3链接https://github.com/.../issues/1950agent 自取详情、评论、标签的入口
4正文快照正文：```…```保证判定依据是事件发生时的版本
为什么

触发词不是装饰，它是技能路由的唯一依据；正文快照与链接并存，是为了「判定有依据、追查有出处」——链接可能指向已编辑后的版本。

FR-4.2首次全量、后续增量P1

issue 的首个事件下发完整正文；后续事件只下发变更内容与本轮指令，不重复整篇正文——历史由会话承担。

待确认：增量粒度（仅变更片段 / 变更前后对比）见 Q-4 上下文超限怎么办。

5.5 执行

FR-5.1平台不决定处理内容P0

一个事件对应一份提示词。至于这份提示词会触发什么处理、产出哪些动作，不由平台决定——平台不维护技能注册表，也不按事件类型硬编码行为。

  • 平台只做三件事：把输入交给执行侧、校验产出、把产出执行出去。
  • 同一事件换一份提示词，行为就应当随之改变，平台代码不动。
边界：平台不控制「做什么」，但必须定义「动作长什么样」，否则无法执行。见 FR-5.3 产出契约：四类动作。
FR-5.2工具调用与沙箱P0

执行侧可以在受控环境内调用工具与命令（读文件、检索、执行命令）。每次调用都要记录工具名、入参与返回。

FR-5.3产出契约：动作与格式P0

执行侧的产出必须落在一个封闭的动作集合里，集合外一律拒绝。动作分两组：默认开放的四类，与已定义但默认关闭的三类——后者不是没有，是需要项目显式开启。

动作全集

动作表达平台行为默认
判定结论 + 证据存档，供后台查；不产生外部副作用开放
标签该 issue 应有的标签全集（目标态）按目标态对齐：多的删、少的加开放
评论槽位名 + 正文同槽位覆盖旧评论，无则新建开放
reaction加 / 减哪个幂等执行开放
建 issue标题 + 正文 + 初始标签按指纹去重、受日配额约束关闭
开 PR分支名 + 标题 + 正文只允许 bot/* 分支，永不 force push关闭
关闭 issue无（不带理由）仅在确定性条件满足时执行，不采信模型自评关闭
后三类为什么默认关闭：它们会改变仓库的可见状态（新建条目、产生分支、关单），误操作的代价远高于改一个标签。要开就在项目级显式打开，默认不给。

产出格式

平台要校验，就必须有格式。产出是一个结构化对象，不是自由文本——自然语言部分只作为评论正文出现。

字段必填说明
verdict是pass / fail；没有判定的纯问答场景可省
evidence否判定依据，字符串数组；后台展示用，不参与执行
actions[]是动作数组，按顺序执行；空数组表示只判定不动作
actions[].type是动作全集里的七种之一，其他值一律拒绝
actions[].payload是按 type 决定形状，见各动作的「表达」列

三条校验规则：

  • 未知 type 拒绝整份产出，不执行任何一条——避免「执行了一半才发现格式错」。
  • 缺必填字段拒绝，错误写进后台记录，可定位到具体字段。
  • 按数组顺序执行，遇失败即停；已成功的动作不回滚，但要记录到哪一步中断。

{
  "verdict": "fail",
  "evidence": ["缺少 iOS 版本", "缺少复现步骤"],
  "actions": [
    { "type": "label",   "payload": { "desired": ["needs-info"], "clear": false } },
    { "type": "comment", "payload": { "slot": "format-review", "body": "缺少 2 项：iOS 版本、复现步骤" } }

槽位怎么落地

「同槽位覆盖」必须有一个可执行的判定依据，否则平台无法知道自己发过哪条评论。

  • 槽位名由执行侧声明，平台不预设，也不校验语义（它只是一个键）。
  • 平台在自己发的评论末尾写隐藏标记（HTML 注释），记录 issue 编号与槽位名，人在 GitHub 页面上看不到。
  • 覆盖时按标记查找：找到就编辑，找不到就新建。
  • 原评论被人删了：标记随之消失，下次就新建一条，并在后台记录「原评论已不存在，已新建」。
  • 同一 issue 上同一槽位只保留一条；不同槽位互不影响（例如「格式评审」和「答复提问」各自一条）。
为什么用目标态（标签）而不是增删指令：平台不知道上一轮发生了什么，只有执行侧清楚这次「应该是什么样」。目标态让对齐成为幂等操作，重复执行结果一致。
FR-5.4标签目标态与删除权P0

标签采用目标态：执行侧给出「这个 issue 最终应该有哪些标签」，平台与当前实际标签对齐。平台拥有删除权，包括删除人手动打的标签。

四条边界：

  • 作用域：只作用于该项目的标签目录（见 6.5 标签目录）。目录即全量，不存在目录外的标签。
  • 空集保护：目标态为空时默认不清空，需显式声明清空意图。
  • 超限整批拒绝：目标集超过项目约定的上限时整批拒绝，不截断——避免出现「删了一半、加了一半」的中间状态。
  • 删除留痕：每次删除记录「原主人是人还是机器」，后台可查、可复盘。
  • 人工删除不构成永久否决：下一轮按目标态重新对齐。确实不想让平台碰某个标签，用项目级的「不自动管理」标记（见 BR-11），那是显式契约，不是靠「删过一次」隐式推断。
前提：执行侧的输入必须包含当前全部标签（见 6.3 占位符清单 的 {{issue.labels}}）与完整目录（含每个标签的含义）。看不到全量就输出目标态，等于盲删。
FR-5.5写回与失败处理P0

动作按顺序执行，失败不得静默：至少有兜底反馈（如普通评论）与后台告警。

  • 不合并 PR。
  • 执行侧没有产出（超时、崩溃、输出不合契约）时，标签与评论保持原状——「没拿到结论」不等于「判定为不合格」。
FR-5.6上下文压缩P0

会话常驻（见 FR-3.4 会话常驻，沙箱随 issue 关闭回收）意味着上下文只会越来越长。超过模型窗口时必须自动压缩，而不是报错、丢消息，或强行开新会话。

触发

  • 阈值从当前模型的上下文窗口现算，不做成配置项——一个固定数字无法同时服务 32K 和 1M 窗口。
  • 两条线：自动压缩线（安全预算的 90%）与硬边界（安全预算本身）。过了硬边界不发送请求，宁可失败也不发一个注定被拒的包。
  • 检查点固定在「请求发出前」：新消息之前、每个轮次边界、工具批次之后。
  • 临近边界时提前提醒模型收尾（两档：还能用多少 / 现在就把必须留存的写下来），每档只响一次。

压缩方式

  • 让模型生成结构化摘要，覆盖切点之前的全部消息——不允许出现「消息离开了上下文却没被摘要覆盖」。
  • 摘要必须保留：目标、约束与偏好、进度（已完成 / 进行中 / 受阻）、关键决策、下一步、关键上下文。精确的文件路径、函数名、报错原文必须原样保留，不能被改写成概述。
  • 压缩区间内读写过的文件清单由系统追加，不依赖模型记忆。

压缩结果怎么放

  • 追加一条 checkpoint，不改写历史。原始对话一条不删，后台始终可查完整记录。
  • 喂给模型的内容 = 从最新 checkpoint 重建；这与后台看到的对话是两套视图，不能混为一谈。
  • 重建时保留最近一段真实消息，而不是只丢一份摘要进去（见下面的保留策略）。

多次压缩

  • 第二次压缩不是重压全量，而是「上一版摘要 + 之后的新增消息」，用更新式提示词：保留旧信息、补充新进展、把「进行中」迁移到「已完成」。
  • 区间过长时分块链式摘要，每块带上上一块的摘要，最终收敛成一份；不允许把多份摘要拼接，那会产生互相矛盾的段落。

工具输出

大结果分三层处理，任何一层都不允许直接丢消息：

阶段处理
执行时抓取有上限，超出部分落文件，正文留截断标记与文件路径
拼摘要时单条工具结果截断到 2000 字符，带「已截断 N 字符」标记
仍超预算时降到 500 字符并丢弃思考块；正文与工具入参不动，也不删任何消息

保留策略：与参考实现的一处刻意偏离

偏离

参考实现压缩后只保留最近的用户消息，助手内容与工具结果只能通过摘要存活。我们不照搬：保留真实最近窗口（含助手输出与工具结果），按 token 预算裁剪，摘要只负责补足窗口之外的旧历史。

理由：摘要一旦漏掉一段报错原文或一个 diff，模型只能重新读文件、重跑命令。长任务里这一次返工，比多占 20k token 贵得多。

代价：必须同时剔除「工具调用已不在窗口内的孤儿结果」，否则模型接口会直接报错。

失败降级

按顺序降级，每一步都有界、可观测：

  1. 预检 —— 用实际要发送的内容估算 token，不发注定失败的请求
  2. 摘要请求短重试 —— 3 次，退避 2 / 4 / 8 秒；鉴权、配额类错误首次即返回，不浪费时间
  3. 一次有界削减 —— 工具结果降到 500 字符、丢弃思考块，其余不动
  4. 分块摘要 —— 长区间切块链式压缩
  5. 兜底 checkpoint —— 沿用上版摘要 + 真实最近窗口 + 明确标记，说明这次是兜底而非正常压缩
  6. 仍超硬边界 —— 拒绝发送请求并明确报错，记录失败原因
空摘要视为失败。看起来压缩成功、实际把上下文丢了，比直接失败更糟——失败至少会被发现。

可观测

  • 每次压缩记录：压缩前后 token、摘要长度、是否走了兜底、第几代。
  • 后台会话详情能标出压缩点，让人知道哪一段历史已经不在模型上下文里了。

写操作仍然只有一条路

提供写类工具不等于 agent 自己发 HTTP。这些工具产出的仍是产出契约里的标准动作（comment / label / create_issue / push_branch），由平台执行、过写回闸门与项目动作开关、每步进审计。工具只是把「要做什么」说清楚，不是绕过治理的旁路。

三条理由（与上一版相同，仍然成立）：绕开治理——自己发评论会跳过槽位覆盖、去重与写回闸门；无法幂等——模型重试一次就可能发两条一样的评论，而目标态交给平台做 diff 天然幂等；权限外溢——给 GitHub 凭证等于把仓库写权限交给执行环境。读操作则可以给，但要满足两条：走平台代理（用平台自己的 App 凭证，token 不进沙箱）、只读且可审计（每次调用记入工具记录）。

当前的落地状态

把自定义工具注入 host 需要 RACP 的 tools/advertise + tool relay，而该通道尚未实现（Host 侧 toolRelay: false，见 docs/tech-plan.md §4.4；本仓 racp-client 的 operation 白名单也明确不含它）。所以现在这 16 个工具以「平台代执行」的形式生效：模型按上面的语义描述要做什么，平台负责落库与写回；提示词据此措辞，不会宣称模型可以直接调用工具名——那在当前链路里是不存在的能力（issue #26 的实测症状就是「工具加载不到」）。契约里的 EXECUTE_CHANNEL_AVAILABLE 标记这件事，通道打通后改它一个常量即可切换措辞。

6配置模型

本章定义配置放在哪、谁能改、怎么生效。

6.1 两个层级

平台级只管两件事：连哪个模型、用哪个 bot 身份。其余全部下放到项目级——同一个平台服务不同仓库时，仓库之间的差异应该只体现在项目配置里。

层级作用范围内容
平台级 所有项目 模型相关：端点地址、模型名、密钥、调用参数
bot 相关：bot 身份、句柄、App 凭证
项目级 单个仓库 执行侧：agent 系统提示词、并发与限流（并发数 / 日配额 / 超时）
触发侧：事件开关、事件提示词模板、评论提及关键词、角色清单
标签：标签目录（与 GitHub 同步）
其他：数据保留期

6.2 继承与覆盖

平台级只有模型与 bot 两组配置，不参与业务默认值。业务侧的「默认」是内置默认（随程序发布的出厂值），不是平台级配置。

  • 项目未配置的项，回落到内置默认。
  • 项目配置整体覆盖内置默认，不追加、不拼接。
  • 配置改动对下一个事件生效；已经开始的那一轮不受影响。
  • 配置随事件打成快照，保证「判定」与「渲染」用的是同一份配置。
注意

「整体覆盖」意味着项目一旦配了模板，就不再继承内置模板的任何内容。这避免了拼接带来的语义混乱，但也要求项目模板自带完整结构（含触发词）。

6.3 占位符清单

标签列表的格式与边界

  • 格式：标签名以逗号加空格分隔，如 bug, needs-info；issue 没有任何标签时渲染为空串，不填「无」之类的占位词。
  • 顺序：沿用 GitHub 返回的顺序，不做排序——保证同一 issue 两次渲染的结果稳定，便于比对。
  • 快照：取本次事件发生时的标签。agent 运行期间标签被别人改了，不影响本轮判断。
关键

标签列表不只是「给 agent 看的一段文本」，它同时是标签目标态的前提（见 FR-5.4 标签目标态与删除权）。执行侧看不到当前全量标签，就无从判断该删该留，目标态必然是盲写。

边界

GitHub 允许标签名里出现逗号。若某仓库确实这么用，分隔符需要改成换行或 |——届时按项目配置指定，默认仍是逗号。

issue 列表的规模控制

这个占位符和标签列表不是一回事：标签最多十几个，issue 可能几千条。全量塞进提示词会瞬间吃光上下文，所以必须带硬约束，不能做成「想给什么就给什么」。

约束默认说明
字段编号 + 状态 + 标题不带正文、评论、标签。判重和找关联靠这三项就够
范围仅 open已关闭的不参与判重；需要时按项目配置改
上限200 条超出按更新时间倒序截断，末尾追加一行说明总数
排除 PR是GitHub 的 issues 接口会把 PR 混进来，必须过滤掉

渲染形态（一行一条）：

#1942 [open] 导出按钮点击后闪退
#1943 [open] 登录后跳转异常
#1951 [open] 列表滚动卡顿
（共 1243 条，仅列最近 200 条）
惰性

只有模板里真的写了 {{repo.issues}} 才去拉数据；没写就不拉。否则每条事件都要跑十几次分页请求，大部分是白花的。

缓存

列表按项目缓存（默认 5 分钟），同一波事件共用一份。缓存过期后重新拉取——判重不需要秒级新鲜度。

不是全文

这是索引，不是内容。agent 想知道某个 issue 具体讲了什么，应该走工具去读那一条，而不是指望列表里带正文。把正文塞进列表会让这个占位符在几百条时就不可用。

6.5 标签目录

平台按项目维护一份标签目录，与 GitHub 仓库保持一致。这份目录既是执行侧的候选集，也是标签目标态的作用域。

字段来源说明
名称GitHub完全一致，含大小写与连字符，不做改写
颜色 / 描述GitHub与仓库同步，平台不单独维护
含义平台给人看的语义说明，GitHub 没有这个字段
分组平台互斥组，如 status / type / priority，同组只留一个
状态平台有效 / 已失效（GitHub 上被删除）

三条同步规则

  • GitHub 是身份的事实源：名称、颜色、是否存在，一律以仓库为准；平台不发明标签、不反向创建。
  • 平台只补语义：含义与分组由人在平台侧维护，同步时不覆盖。
  • 漂移要显性：仓库新增的标签自动进目录但含义为空；仓库删除的标签标记失效，不再出现在目标态里。
保护

含义为空的标签不进入自动对齐范围。执行侧不知道它是什么意思，就不该删它。等有人补上含义，才纳入管理。

时机

目录在处理事件前按需刷新（有有效期，不必每条事件都请求一次）。避免频繁调用，也避免拿着过期目录做删除判断。

目录怎么交给执行侧

目录不作为模板占位符，由平台在装配输入时固定注入，位置紧跟系统提示词。原因：它和系统提示词一样是常驻信息，放进模板容易被漏写；而漏写的后果是「看不到全量标签却输出目标态」——直接盲删。

信息从哪来说明
目录：可选标签平台固定注入每行「名称 | 含义 | 分组」，只列含义非空的（即可管理范围）
当前标签：已选占位符 {{issue.labels}}这条 issue 现在挂着哪些
区别

目录回答「有哪些可以选」，{{issue.labels}} 回答「现在选了哪些」。两者缺一，目标态都无从判断。

6.6 评论触发配置

评论事件的两个闸门依赖项目级预先定义的数据。闸门里只能选，不能临时填写——否则每换一个人就要改一次闸门。

提及关键词

项必填说明
关键词是要命中的名字，如 pi-bot。可配多个（句柄、别名、历史叫法）
是否区分大小写否默认不区分

命中规则见 FR-2.5 提及关键词与合法提及：@ 开头、紧跟关键词、关键词后必须是分隔符。

角色清单

项目级维护一份角色清单，每个角色要么按 GitHub 作者关联定义，要么按具体人定义：

项取值说明
角色名如「维护者」「值班同学」给人看，闸门里按这个名字选
判定方式作者关联 / 指定成员二选一
作者关联OWNER / MEMBER / COLLABORATOR
CONTRIBUTOR / FIRST_TIME_CONTRIBUTOR / FIRST_TIMER / NONE		GitHub 随每条评论直接给出，不需要额外查询
指定成员GitHub 个人账号（login），如 alice只支持个人，不支持组织或团队
为什么

成员用 login 而不是邮箱：协作者接口本身不返回邮箱，用户邮箱默认不公开（API 返回空），且一个人可能有多个邮箱、随时会换。login 才是 GitHub 上的稳定标识。

两个坑

login 会变：用户改名后旧 login 会被释放给他人注册。因此保存配置时把 login 解析成用户 id 一起存，匹配时以 id 为准。
拼错会静默失效：写错一个字母，那个人永远触发不了且没有报错。保存时校验账号是否存在，不存在就拒绝。

关系

角色清单是定义，评论闸门是引用。「是否限定角色」打开后，从这里选一个或多个；想加人只改清单，不用动闸门。

6.7 agent 系统提示词与执行限额

这两组都在项目级，因为不同仓库对 agent 的角色期待与承载能力本来就不一样。

系统提示词

常驻的角色设定与硬约束，每次调用都带；它不是某一次事件的具体指令。与事件模板的分工：

维度系统提示词事件提示词模板
回答什么你是谁、边界在哪、怎么说话这一次要做什么
生效方式每次调用都携带触发时渲染后携带
变化频率稳定，很少改随事件类型不同
归属项目级（未配置用内置默认）项目级（按事件分别配置）
为什么

系统提示词放项目级而非平台级：同一套平台服务不同仓库时，"这个项目的 agent 应该是什么角色"是仓库自己的事，平台不该替它决定。

并发与限额

项含义触顶行为
并发数同一项目同时最多几个会话在跑排队等待，不丢弃
日配额每天最多处理多少个事件拒绝处理并记录原因，可查
单轮超时一轮执行的最长时长终止并记为超时，不自动重试
为什么不设平台级限额：不同仓库的负载差异很大，用一个全局值卡所有项目只会让轻的浪费、重的排队。平台只在部署层面给出总量级约束（见 9 非功能需求），不做业务限流。

7业务规则

本章是跨需求的硬规则，实现与测试都以此为准。

编号规则内容
BR-1会话唯一同一 issue 在同一时刻只能有一个活跃会话；映射一对一，不允许并发创建。
BR-2串行消费同一 issue 的轮次串行；跨 issue 并行。
BR-3事件幂等投递级、事件级、内容级三层去重（见 FR-3.5 幂等：三层去重）；同 issue 内同内容评论只处理一次；上一轮失败的不算重复。
BR-4增量投喂后续事件只下发变更与指令，不重复整篇正文。
BR-5会话域隔离issue 与 PR 各自独立会话，上下文不互通。
BR-6不触发也留痕未通过开关或闸门的事件，必须记录判定结果与原因，可在后台查询。
BR-7失败可见执行失败必须有可见反馈（兜底评论或后台告警），不得静默。
BR-8配置即快照同一事件内，判定用的配置与渲染用的配置必须是同一份快照。
BR-9标签以目录为准标签身份以该项目的标签目录为准，与 GitHub 保持一致；目录外不存在可打的标签。
BR-10删除留痕任何标签删除都要记录原主人（人 / 机器）与删除原因，可复盘。
BR-11标签管辖边界人若不想让平台动某个标签，在项目级把该标签标记为「不自动管理」；标记后平台既不删也不加。未标记的标签按目标态正常对齐——人工删除不构成永久否决。
BR-12无语义不删目录里含义为空的标签，不参与自动对齐——不知道语义就不做删除判断。

10验收标准

本章是可勾选的验收清单，每条都能用一次真实操作验证。

  • AC-1同一 issue 先后触发 issues.opened 与 issues.edited，两次处理共用同一个会话 ID。
  • AC-2打开后台的该 issue 会话，能看到两轮的完整对话，且第二轮不再重复询问第一轮已确认的信息。
  • AC-3把某事件的开关改为关闭后，新事件不再进入处理，后台能看到该事件被记为"未触发"及原因。
  • AC-4在项目模板里写两次 {{issue.number}}，两处都被替换为真实编号。
  • AC-5评论未 @ 机器人时（且「是否提及才触发」为开启），该评论不触发；@ 之后触发。
  • AC-6issue 关闭后新增评论（且「是否响应已关闭」为关闭），不触发。
  • AC-7同一 issue 连续快速来三个事件，处理顺序与到达顺序一致，没有并发交错。
  • AC-8同一条 webhook 重放一次，不产生新的轮次。
  • AC-9后台能查到该轮每次工具调用的名称、入参摘要与结果。
  • AC-10后台能查到该轮 prompt 与 completion 的 token 数，并折算成本。
  • AC-11项目未配置某事件模板时，使用平台默认模板，行为与内置一致。
  • AC-12修改项目模板后，下一个事件立即生效，进行中的轮次不受影响。
  • AC-13作者补齐缺失信息后，同槽位的评论被编辑更新（不新增一条），且「需补充信息」标签被自动移除。
  • AC-14执行侧把目标态写成删除一个含义为空的标签时，该删除被拒绝并记录原因。
  • AC-15维护者手动删除某标签后，后续轮次即使目标态里包含它，也不会被自动加回。
  • AC-16执行侧超时未产出时，issue 上的标签与评论保持执行前状态，未被误删或误加。
  • AC-17评论写 @pi-bot帮我看看（无分隔符）时不触发；写 @pi-bot 帮我看看 时触发。
  • AC-21模板里写 {{repo.issues}} 时，渲染结果只含编号/状态/标题，不含 PR；超过上限时有「共 N 条，仅列最近 M 条」的说明。
  • AC-22模板里没有该占位符时，处理该事件不产生任何 issue 列表相关的请求。
  • AC-19同一 issue 内连续两次发相同内容的评论，第二次不触发处理，后台可查到「因重复内容跳过」的记录。
  • AC-20上一轮执行失败后，用户原样重发同一内容，能够正常触发（不被内容去重挡住）。
  • AC-18不在项目角色清单内的人 @ 机器人，且「是否限定角色」为开启时，该评论不触发。
  • AC-24同一会话压缩两次后，模型仍能复述第一轮确定的目标与硬约束（验证摘要没有丢关键信息）。
  • AC-25压缩发生后，后台能看到压缩记录（前后 token、是否兜底、第几代），且原始对话一条不少。
  • AC-23issue 关闭后沙箱被回收，重新打开并触发时复用原会话：历史上下文仍在，沙箱自动重建。

11决策记录

本章保留历次拍板的结论与理由，便于日后回看「当初为什么这么定」。未定的项会标出来。

Q-1占位符清单 · 已定

已定：现有占位符全部列为正式，不再区分待定。最终清单见 6.3 占位符清单。

Q-2未知占位符怎么处理 · 已定

已定：原样进入提示词，不做替换，同时记一条配置告警。

理由：替换成空串会让模板悄悄变成残句，比留一个明显的 {{issue.foo}} 更难发现。
Q-3会话何时结束 · 已定

已定：会话没有结束状态。issue 随时可能被重新打开，因此只有 issue 有「关闭」这个状态，会话本身不归档。

关闭时做什么：只回收对应的 agent 沙箱（容器），会话与全部记录保留；重开时直接复用原会话。见 FR-3.4 会话常驻，沙箱随 issue 关闭回收。
Q-4上下文超限怎么办 · 已定

已定：参考 pi-desktop 的 checkpoint 压缩机制做自动压缩，具体要求见 FR-5.6 上下文压缩。

三处关键取舍：

  • 阈值现算不配置：从当前模型窗口推导「自动压缩线（90%）」与「硬边界」，避免一个固定数字吃掉不同模型的差异。
  • 追加 checkpoint 不改写历史：与「会话常驻、记录永久保留」天然一致，压缩只改喂给模型的那份视图。
  • 偏离参考实现一处：压缩后保留真实最近窗口（含助手输出与工具结果），而不是只留用户消息。摘要漏掉一段报错就得重跑命令，返工成本高于多占的 token。
为什么不自创：长会话压缩的坑集中在「摘要的摘要」与「工具结果丢失」两处，已有实现踩过一遍并留下多轮补丁，直接对齐比重新试验便宜。
Q-5事件进不进会话，谁说了算 · 已定

已定：项目配置说了算。事件开关、触发条件、模板全在项目级，平台只给一套内置默认值。

理由：硬编码事件语义会让「同一套平台服务不同仓库」这件事失效。
Q-6一条模板能不能挂多个技能 · 已定

已定：一个事件对应一个提示词；具体触发什么处理不由平台控制。平台不维护技能注册表，只执行产出的四类动作（FR-5.1 平台不决定处理内容 / FR-5.3 产出契约：四类动作）。

推论：多技能串行、阶段间结果传递这类复杂度交给提示词与执行侧自行处理，平台不介入。

12附录 · 术语

本章统一口径，避免同一概念多种叫法。

术语定义
事件GitHub 投递到平台的一次通知，由「事件类型 + 动作」共同确定，如 issues.opened。
触发某事件通过开关与闸门判断，被允许进入处理。
会话一个 issue 在 agent 侧的身份，与 issue 同生命周期，持有历史上下文，跨事件复用；没有结束状态。
轮次会话内的一次完整执行，由一条提示词驱动。
模板项目配置里的事件提示词，含占位符，触发时渲染成实际指令。
占位符模板中形如 {{issue.author}} 的变量，渲染时替换为真实值。
闸门评论事件特有的附加判断条件，如是否提及、是否限定角色。
写回平台把处理结果落到 GitHub 的动作：评论、打标、建 issue、开 PR、关闭 issue。后三类默认关闭，需项目显式开启（见 FR-5.3 产出契约）。
目标态执行侧给出的「该 issue 最终应有哪些标签」的完整集合；平台与当前状态对齐，多的删、少的加。
标签目录平台按项目维护的标签清单，身份与 GitHub 仓库一致，语义（含义、分组）由平台侧补充。
槽位评论的固定位置标识。同一槽位只保留一条评论，更新时覆盖而不是新发。
提及关键词项目级配置的触发名字（如 pi-bot）。评论里 @ 关键词且其后是分隔符，才算合法提及。
角色清单项目级定义的可触发角色集合，每个角色按作者关联或指定成员（GitHub 个人账号）判定；闸门只能从中引用，不支持组织与团队。
