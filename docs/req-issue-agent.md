# Issue Agent 需求 · v0.3（极简版）

> v0.1 的三层架构已废弃。v0.2 的两处错误在 v0.3 修正：
>
> 1. 技能命中不是「首个 token」，是「正文任意位置的 `/名字`」；
> 2. `/技能名` 不会把技能正文塞给 agent，只是要求 agent 去加载它。  
>    状态：**已定稿（2026-11-11 15:35）**。P1 / P3 已拍板，记录见 §7。

---

## 0. 一句话

**一个 issue 绑定一个 agent；issue 内容在会话启动时就在上下文里；技能只是「一份可按需加载的提示词文档」，`/名字` 只是替模型把"该加载哪份"这件事说死。**

没有流程引擎、没有状态机、没有闸门、没有调度器。

---

## 1. 模型

### 1.1 只剩两层

| 层         | 内容                                |
| --------- | --------------------------------- |
| **输入**    | 人的 @ 消息；GitHub 事件按模板生成的消息         |
| **Agent** | 一个 issue 一个，串行处理消息，产出评论 / 标签 / 代码 |

### 1.2 一条消息的生命周期

```
收到输入
  → 去重（同 issue + 同文本，窗口内只跑一次）
  → 加 reaction（表示已收到，排队中）
  → 扫描正文里的 /技能名：命中的从正文摘掉，换成「先加载这几个技能」的指令
  → 进 issue 的串行队列，交给 agent
  → agent 按需用 Skill 工具拉正文，按正文干活
  → 产出：默认一条评论；标签 / 代码必须显式调工具
  → 去掉 reaction
```

### 1.3 技能是什么

一份 markdown 文档。**正文不会预先出现在上下文里**，只有「目录」常驻。

| 东西                    | 在哪                 | 什么时候进上下文            |
| --------------------- | ------------------ | ------------------- |
| 技能目录（id + 名字 + 一句话描述） | 系统提示的 `# Skills` 段 | 会话启动时，一直有           |
| 技能正文（那份提示词）           | 技能文件               | 模型调 `Skill` 工具时，按需拉 |

命中规则（照抄 pi-desktop）：正文任意位置出现 `/名字`，且 `/` 前是行首或空白，且名字精确匹配目录里的 id。

```
@bot /label-triage            命中（/ 前是空格）
@bot 看看格式 /format-check    命中（/ 前是空格，位置任意）
@bot/label-triage             不命中（/ 前是 t）
@bot /label-tri               不命中（没有这个 id，当普通文本）
```

不命中不做任何提示，原样当自然语言。

### 1.4 事件是什么

事件 = 用固定模板生成一条消息，投给 agent。模板可以点名技能，也可以不点。

| 事件                                | 投递 | 模板大意                                     |
| --------------------------------- | -- | ---------------------------------------- |
| `issues.opened`                   | 是  | 新 issue，用 `format-check` 看一下，不合规就告诉作者补什么 |
| `issues.edited`（仅标题/正文变更）         | 是  | 正文变了，重新看一遍                               |
| `issues.reopened`                 | 否  | —                                        |
| `issue_comment` 里 @ 了它            | 是  | 用户原话                                     |
| `labeled` / `assigned` / `closed` | 否  | 避免 AI 自己打标后触发自己                          |
| bot 自己创建、dependabot 创建            | 否  | 防自我循环                                    |

「仅对新增生效」的真实含义 = **永不回填历史 issue**，不是「edited 不触发」。

正文里的 `@bot` 不算 mention。GitHub 不会为 issue 正文里的 @ 产生独立事件，所以 opened 只跑一次；只有评论里的 @ 才是 mention 触发。

### 1.5 两种输入到底差在哪

agent 启动时，issue 正文、历史、技能目录都已经在上下文里。所以：

| 输入                     | 系统提示              | 这一条用户消息                                           |
| ---------------------- | ----------------- | ------------------------------------------------- |
| `@bot 给这个 issue 重新打标签` | issue + 历史 + 技能目录 | 原话                                                |
| `@bot /label-triage`   | **完全相同**          | 原话删掉 `/label-triage`，前面加一句「先加载 label-triage，按它执行」 |

差别只有一句「先加载谁」。不是「一个有技能一个没有」——自然语言下模型看到目录，也可能自己决定加载 `label-triage`。

所以 `/` 的价值是**确定性**：把"要不要加载、加载哪个"从模型手里拿走。它和自然语言走的是同一条 `Skill` 工具通道，不是两条路径。

## 2. 技能加载链路（参考 pi-desktop）

### 2.1 流程图

```
                     会话启动
                        │
        ┌───────────────┴───────────────┐
        │  扫描技能目录（两级）           │
        │  内置/全局：<data>/skills/     │
        │  项目级：.github/pi-bot/skills/│
        │  两种形状：<id>.md / <名字>/SKILL.md
        └───────────────┬───────────────┘
                        │
        ┌───────────────┴───────────────┐
        │  解析每个文档                   │
        │  · frontmatter: name / description
        │  · 正文必须非空                 │
        │  · id 由 name slug 或路径派生   │
        │  · 单文档 ≤128KB，最多 128 个    │
        └───────────────┬───────────────┘
                        │
        ┌───────────────┴───────────────┐
        │  合并与过滤                     │
        │  · 项目同名 → 覆盖全局（整体替换）
        │  · 同 id 只留第一个             │
        │  · enabled=false → 不出现       │
        └───────────────┬───────────────┘
                        │
        ┌───────────────┴───────────────┐
        │  只把「目录」写进系统提示        │
        │  # Skills                      │
        │  - `format-check` — 格式检查: … │
        │  - `label-triage` — 打标签: …   │
        │  正文一个字都不进                 │
        └───────────────┬───────────────┘
                        │
   ┌────────────────────┴────────────────────┐
   │                                         │
用户发消息                              模型处理中
   │                                         │
扫描 /token（任意位置，                  看到目录，判断
/ 前须为行首或空白）                     哪个技能适用
   │                                         │
   ├─ 命中 → 删 token，                      ├─ 需要 → 调 Skill(id)
   │        加「先加载这些 id」               │         → 返回正文
   │                                         │         → 正文进入上下文
   └─ 未命中 → 正文原样                      └─ 不需要 → 直接回答
   │                                         │
   └──────────────→ 交给 agent ←─────────────┘
                        │
                   按技能正文执行
                        │
              产出：评论 / 标签 / 代码
```

### 2.2 每个阶段的事实依据

| 阶段 | pi-desktop 的做法                                                   | 位置                                                       |                                                                               |
| -- | ---------------------------------------------------------------- | -------------------------------------------------------- | ----------------------------------------------------------------------------- |
| 扫描 | 两级目录；`*.md` 与 `<名字>/SKILL.md` 两种形状都收                             | `host-core/src/user_skills.rs` `scan_level`              |                                                                               |
| 解析 | frontmatter 取 `name`/`description`；正文空则丢弃；id 由 name slug 优先、路径兜底 | 同上                                                       |                                                                               |
| 上限 | 128 个技能；单文档 128KB；目录型技能单资源 2MB、整包 16MB                           | `MAX_SKILLS` / `MAX_SKILL_BYTES`                         |                                                                               |
| 覆盖 | 项目同名整体替换全局，不合并字段                                                 | `merge_active_records`                                   |                                                                               |
| 注入 | **只注入目录**：`id — 名字: 描述`；正文不注入                                    | `agent-runtime/src/plugin-skills-prompt.ts`              |                                                                               |
| 加载 | 模型调 `Skill` 工具，按 id 取正文                                          | 同上，D174「技能由模型自取」                                         |                                                                               |
| 触发 | 正则 \`/(^                                                         | \s)/([^\s]+)/g\` 扫全正文；命中则删 token，并前置「先调 Skill 工具加载这些 id」 | `shared/src/composer-trigger.ts` `findSkillMentions` / `composeMentionPrompt` |
| 增量 | 系统提示按 section 更新，技能变了只 append 变化项                                | `pluginSkillsPromptSections`                             |                                                                               |

### 2.3 对本项目的三条结论

1. **正文不要预加载。** 目录常驻、正文按需，才能做到「项目里放 10 个技能也不撑爆上下文」。
2. **`/技能名` 不是「塞正文」，是「指定加载」。** 它和自然语言共用 `Skill` 工具，所以两者行为天然一致，不需要两套代码。
3. **命中的边界照抄：任意位置 + `/` 前必须行首或空白 + id 精确匹配。** 这正好等于你说的「只要包含就算」，同时排除 `@bot/label-triage` 这种粘在一起的写法。

## 3. 配置项（全部，5 个）

| 配置                             | 默认                                               | 说明                             |
| ------------------------------ | ------------------------------------------------ | ------------------------------ |
| `skills/`                      | 内置 3 个：`format-check`、`label-triage`、`review-pr` | 项目同名整体覆盖                       |
| `on_opened`                    | `format-check`                                   | 新 issue 投递哪条消息；置空则不投递          |
| `on_edited`                    | `format-check`                                   | 标题/正文变更投递哪条消息；置空则不投递           |
| `auto_label_after_format_pass` | `false`                                          | 格式检查通过后，自动再投递一次 `label-triage` |
| `project_prompt`               | 空                                                | 项目规范：合格格式长什么样、标签词表、缺什么该提示什么    |

「格式检查提示词里要写什么」= `project_prompt` + `format-check` 技能正文。项目只改 `project_prompt` 就能换口径，不用碰技能。

## 5. 硬规则（只有 5 条）

1. **@ 仅管理员**。非管理员回一次「无权限」，同 issue 只回一次。
2. **同 issue 同文本永久幂等**。归一化（去 @、去空白、去标点）后算 hash，永久只执行一次；重复请求直接返回上次结果。
3. **一个 issue 一个 agent，串行**。排队时加 reaction，处理完移除。
4. **默认产出只有评论**。标签、代码、PR 必须显式调工具。
5. **永不回填**。任何接入、重置、升级动作，都不对历史 issue 产生写操作。

## 6. 相比 v0.1 砍掉了什么

| 砍掉              | 原因                     |
| --------------- | ---------------------- |
| 触发器 / 技能 / 策略三层 | 只需要「消息来源 + 技能」         |
| 调度器             | 一个 issue 一个 agent      |
| 意图路由            | 命中就加载，没命中就是自然语言        |
| 多意图编排           | 一条消息一个回合，模型自己决定做几件事    |
| 会话作用域隔离         | 一个 issue 一个 agent，天然隔离 |
| 状态机 / 徽章 / 闸门   | 不存在「issue 走到第几步」       |
| 限流 / 预算 / 配额    | @ 仅管理员                 |
| 提示词注入专项防护       | 管理员专属通道                |
| 批量打标            | 本版不做                   |

## 7. 拍板记录

| #      | 结论                                           | 落点            |
| ------ | -------------------------------------------- | ------------- |
| **P1** | opened 仍要跑格式检查；正文 @ 了 bot 不重复跑               | §1.4 末段、§4 A6 |
| **P2** | 任意位置包含即命中，`/` 前须行首或空白，id 精确匹配                | §1.3、§2.3     |
| **P3** | 永久幂等，`hash(issue + 归一化文本)`，归一化 = 去 @、去空白、去标点 | §5 第 2 条      |

**P3 的副作用（已知并接受）**：正文后来变了，同样的指令也不会重新执行。要重跑就换一种说法。这是刻意的——同一句话在同一 issue 上永远只烧一次钱。
