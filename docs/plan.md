## 1. 目标与非目标

### 1.1 目标

单组织自托管的平台，响应 GitHub issue / pull request 事件，用 PI SDK 驱动 agent 分析仓库，并把结果写回 GitHub：

1. 自动给 issue 分类打标
2. 判断 issue 是否符合仓库的报告标准，并自动回复
3. 被授权人员 `@机器人 /命令` 时执行技能（`/review-pr`、`/issue-triage`、`/issue-repro` 等）
4. 主动创建 issue（去重 + 配额）
5. 自动推 `bot/*` 分支并开 PR
6. Web 统计面板：吞吐、失败分布、成本、质量信号、审计

### 1.2 非目标（v1）

- 多租户 SaaS、计费、租户隔离
- GitLab / GHES / Bitbucket
- 合并 PR（代码层不实现）
- 改写贡献者分支
- 事前审批、事后复核流程
- Issue/PR 之外的自然语言对话

## 2. 已确认决策

| # | 决策 | 内容 |
|---|---|---|
| D1 | 部署形态 | 单组织自托管，一个 GitHub Org、少量仓库，单机 |
| D2 | 代码托管 | GitHub.com + **GitHub App**（安装级 token，1 小时过期，权限可收窄，可审计） |
| D3 | 写操作 | 打标 / 评论 / 建 issue / 推 commit / 开 PR **全自动**；**没有合并能力** |
| D4 | 分析深度 | 真实检出：clone + 装依赖 + 跑测试，每任务独立 worktree |
| D5 | 沙箱 | Docker，一任务一容器，按结果销毁；agent 在宿主机，只有命令进容器 |
| D6 | 置信阈值 | **不设**。判定靠证据，不靠模型自评分；关闭 issue 走确定性条件 |
| D7 | 网络 | 公网放行，私网与云元数据地址阻断；完全断网为高风险任务的加固档 |
| D8 | 人工参与 | 取消事前审批与事后复核，只保留异常兜底通知 |
| D9 | 规模 | < 100 事件/天，2–4 并发 |

## 3. 核心约束与安全模型

D3 + D4 组合起来就是这台主机的核心矛盾：**既有外来代码的执行权，又有仓库的写凭证**。取消阈值、全自动之后，防止误判的缓冲垫没有了，唯一能依靠的是「结构上做不到坏事」。

两种常见做法都不可接受：

- 把 agent 也塞进容器 —— 模型密钥跟着进去，陌生代码与 agent 同处一个进程空间，结论可被篡改
- 不隔离、靠提示词约束 —— `postinstall` 一行脚本就能反弹 shell

采用的第三条路：**把「想」和「做」分开**。agent 在门外推理，容器只负责跑命令；凭证永不进入不可信一侧；agent 的产出必须先过结构化校验才能变成 GitHub 写操作。

## 4. 架构与执行边界

### 4.1 组件

```
GitHub（App webhook / REST）
        │
        ▼
控制面（常驻）：webhook 验签 · 事件去重 · 任务队列 · 重试 · 熔断 · 写执行器 · 指标
        │  拉起一次性 worker（pi-host + agent-runtime）
        ▼
容器（不可信）：worktree 挂载 / 装依赖 / 跑测试 —— 无凭证、无 socket
```

### 4.2 实际执行位置

| 东西 | 在哪 | 隔离 |
|---|---|---|
| 控制面 / pi-host / agent / 凭证 | 宿主机进程 | 无（可信侧） |
| `pnpm install`、测试、构建、每条命令 | 容器内 | namespace + cgroup + cap-drop + 只读根 fs + 非 root |
| 仓库文件 | 同一份 bind mount | 宿主直接读写，容器只见 `/work` |
| 命令与输出 | 跨边界 | 唯一数据通道（`docker exec`） |

### 4.3 为什么 agent 不在容器里

1. **同一个进程空间。** 陌生代码与 agent 共处一容器，前者能读后者的环境变量（模型 key 就在里面）、能 `ptrace` 它、能杀掉它。
2. **结论可被篡改。** agent 的判定决定要不要推 commit、要不要发评论；判决者与被观察者同处一室，判定不可信。
3. **工程代价。** 镜像从约 400 MB 涨到 1.5 GB+；transcript 由 Rust `host-core` 独占写入，塞进一次性容器就得每任务一个库，或把权威数据库挂进不可信环境。

若坚持 agent 进容器，代价：需要能注入模型 key 的宿主侧出口代理、接受每任务独立 transcript 库、放弃「结论不可被篡改」。

### 4.4 复用 `apps/pi-host`，不重写运行时

仓库已提供的能力直接复用：会话与记录（`session/create｜attach｜history｜compact`，transcript 落 Rust `host-core`）、轮次控制（`turn/start｜cancel｜interrupt｜get`）、审批钩子（`approval/respond`）、工具面与事件（`workspace/*`、`toolShell`、`workspace/diff`，事件流带游标与重放）。

保留一层 `JobRunner` 接口，将来若单进程更划算可整体换成 in-process。

## 5. 任务信封

agent 拿不到 GitHub 凭证，只能交出结构化结果，由控制面校验后决定执行哪些动作。字段不合规的动作直接丢弃并记为解析失败。

```jsonc
{
  "verdict": { "kind": "issue", "labels": ["bug"],
               "evidence": [ { "rule": "has-repro-steps", "quote": "…" } ] },
  "actions": [
    { "intent": "comment",      "body": "…" },
    { "intent": "label",        "add": ["bug"] },
    { "intent": "create_issue", "title": "…", "fingerprint": "dep-vuln:x" },
    { "intent": "push_branch",  "branch": "bot/fix-123", "openPr": true }
  ],
  "usage": { "inputTokens": 0, "outputTokens": 0, "costUsd": 0 }
}
```

**信封里故意没有 `confidence`。** 自评分不可核查、没有消费方，而且最容易被顺手改回阈值。可核查的是 `evidence`——每条判定附命中的规则与原文片段。

## 6. 能力清单

### 6.1 分类打标

- 触发：`issues.opened` / `edited` / `reopened`
- 标签来自仓库 `.github/pi-bot.yml`，不发明新标签；默认集 `bug / feature / question / docs / needs-info / area/*`
- **不设信心阈值**：一律打标；判定附命中的规则与原文证据
- 幂等重算：issue 被编辑后重判，只增删**自己打过的**标签，人打过的不动

### 6.2 标准合规检查与自动回复

- 规则来源：issue 模板必填项 + 配置里的显式检查（复现步骤、版本号、日志）
- 判定结构化：每条规则 pass/fail 附 issue 原文证据
- 不合规 → 一条评论列出缺什么、附模板片段，打 `needs-info`
- **只在缺失项集合变化时再回复**；同一句话不催第二次

### 6.3 主动建 issue

- 场景：PR review 顺带发现的独立缺陷、依赖与回归告警；同类 issue 汇总默认关闭
- 去重键 `(repo, 指纹)`：命中则追加评论，不新开
- 日配额默认 10 个/仓库，超限写入待办队列而不创建
- 只创建、不关闭

### 6.4 @ 触发的技能指令

- 门禁看 `author_association`：OWNER / MEMBER / COLLABORATOR 或白名单；机器人账号忽略
- 命令即技能（markdown frontmatter），仓库可自带技能
- 同一 `head_sha` 重跑是空操作；换新提交则取代上一条评论
- 10 秒内给出回应（表情或一行确认）

### 6.5 Web 统计面板

- 吞吐：事件量、任务结果分布（成功/失败/超时/熔断/解析失败）、p50–p95 耗时、队列深度
- 质量：**自动执行后被人改回**的次数与比例（事后复核取消后唯一的质量指标）
- 成本：按仓库/命令拆的 token 与金额，最贵的十个任务
- 审计：谁触发、跑了哪个提交、写了什么，可导出

## 7. 权限与闸门

| 动作 | 状态 | 约束 |
|---|---|---|
| 打标签 | 自动 | 无阈值；只增删自己打过的 |
| 发评论 | 自动 | 结构化校验 + 隐藏任务标记 + 频率限制 |
| 创建 issue | 自动 | 去重键命中则追加评论；日配额 10/仓库 |
| 推 commit / 开 PR | 自动 | 只到 `bot/*` 分支；永不强推，永不改写贡献者分支 |
| 关闭 issue | 有条件 | `needs-info` 标签 + 缺失项 48h 未变 + 无人回复（确定性条件） |
| 合并 | **不存在** | 代码层不实现 merge；分支保护强制人工 review 兜底 |

### 7.1 「没有合并权限」落在哪里

GitHub 的权限粒度到不了「能推 commit 但不能合并」这一档——merge 与推 commit 共用 `Contents: write`。因此是三层保险：

1. 代码层面不存在 merge 调用
2. 受保护分支要求人工 review 与必需检查全绿
3. 每次写操作进审计，并与 GitHub 侧审计对账

### 7.2 权限全授予的对应措施

installation token 本身 1 小时过期、只作用域到配置的仓库、只存在控制面进程、每次写操作留痕。即使 agent 被注入，损失上限是「一个仓库、一小时内」。

## 8. 沙箱与网络

### 8.1 容器规格

```sh
docker run -d --init --rm \
  --name pi-job-<id> \
  --user 1001:1001 \
  --read-only --tmpfs /tmp:rw,size=512m,noexec,nosuid \
  --cap-drop ALL --security-opt no-new-privileges \
  --pids-limit 512 --memory 2g --memory-swap 2g --cpus 2 \
  --ulimit nofile=4096 \
  -v /srv/pi/jobs/<id>/work:/work:rw \
  -v pi-dep-cache:/cache:ro \
  -w /work \
  pi-worker:<toolchain> sleep infinity
```

常驻空闲进程，按需 `docker exec` 执行命令。

### 8.2 网络策略

不强制断网——装依赖本来就要公网。容器里没有任何可偷的凭证，外传不是主要威胁；真正的威胁是把它当跳板扫内网、打云元数据。因此按「能不能去哪」切：

- **放行**：公网（包管理器仓库、公共 CDN）
- **阻断**：`10/8`、`172.16/12`、`192.168/16`、`169.254/16`、`::1`
- **可选加固**：高风险任务（会自动推分支的）可切到 `--network=none`

实现二选一：出口代理 + allowlist，或 docker network + iptables DROP 私网段。两者都要覆盖 IPv6。

### 8.3 容器生命周期

| 结果 | 容器 | worktree |
|---|---|---|
| 成功 | 立即销毁 | 保留 24h 供查 diff，之后回收 |
| 失败（非超时） | 保留 1h 可复现，之后强删 | 保留 1h |
| 超时 / 熔断 | 立即 SIGKILL | 立即回收 |
| 磁盘水位 > 85% | 强制清理最旧的失败容器 | 无视保留期，清最旧 |

### 8.4 四条红线

1. docker socket 只挂控制面（socket 等价于宿主机 root）
2. 容器里没有任何 token，模型请求由宿主代发
3. 能力全砍：`cap-drop ALL`、只读根文件系统、非 root、pids 与内存上限
4. 挂载只给一份 worktree，不给宿主目录、不给数据目录

### 8.5 预检（`pi-bot doctor`，不通过拒绝启动）

daemon 可达 · 磁盘 ≥ 20 GB · worker 镜像存在且工具链匹配 · 金丝雀容器里访问 `169.254.169.254` 确实失败 · `--memory` / `--cpus` 真的生效。

## 9. 时间、重试与熔断

### 9.1 三层时间闸

| 层级 | 默认 | 超时处置 |
|---|---|---|
| 单条命令 | 120s（install/build 类放宽到 300s） | 杀掉该命令，记 `command-timeout`，让 agent 换策略 |
| 单任务 | 20min（`/review-pr` 30min） | kill 容器 + 中断轮次，记 `timed-out` |
| 队列等待 | 10min | 回复「排队过长，请稍后」，不占并发 |

超时的任务**不自动重试**，只接受人工 `/retry`。

### 9.2 重试矩阵

| 错误 | 重试 | 做法 |
|---|---|---|
| 429 限流 | 是 | 优先读 `retry-after`，否则指数退避 + 抖动，最多 4 次 |
| 5xx / 网络抖动 | 是 | 同上，最多 3 次 |
| 容器崩溃 | 最多 1 次 | 第二次仍崩判为环境问题，转异常兜底 |
| 401 / 403 / 其他 4xx | 否 | 转异常兜底 |
| 结果解析失败 | 否 | 重试会得到同样的坏输出，需调 prompt |
| 命令级超时 | 否 | 记为失败，交给 agent 换策略 |

两条硬约束：**非幂等写不盲目重试**（评论、打标、建 issue 重试前先查现状，靠隐藏标记与去重键兜住）；**连续 5 次 429 触发全局熔断 15 分钟**。

### 9.3 重复输出熔断

AI 卡在同一个思路里反复输出同一段内容时，表现不是「慢」，是按 token 计费的无限循环；而且重复推理往往意味着上下文已被污染，重试只会重走一遍。

触发条件（满足任一即中止本轮）：

1. **段落重复**：归一化（去空白、去标点）后，同一段 ≥ 200 字符的窗口在一次任务里出现 ≥ 3 次
2. **低增量**：最近 4k 输出 token 里新增 n-gram 占比 < 5%
3. **工具循环**：同一工具、同一参数连续调用 3 次，且没有产生新的文件或测试结果变化

处置：`turn/interrupt` 打断本轮 → 任务标 `degenerate-output` → **不自动重试** → 已产出的结构化结果照样校验入库 → 进异常兜底通知。

### 9.4 异常兜底

唯一保留的人工触点，只在失败时出现：超时、熔断、认证失败、解析失败、容器崩溃。正常路径完全静默。

## 10. 非功能要求

- 事件到首个写操作 p95 < 90s（判定类）、< 15min（`/review-pr`）
- 至少一次处理 + 幂等写：webhook 重投不得重复评论
- 每个失败都有分类（`auth` / `rate_limit` / `sandbox` / `model` / `parse` / `github_api` / `timeout` / `degenerate-output`）
- 优雅停机：进行中的任务完成或重新入队，不留半成品写
- 密钥只在宿主环境或系统密钥库，日志不得出现
- 本地可复现：录制的 webhook 载荷能在不触达 GitHub 的情况下重放整个任务
- 仓库配置加载时做 schema 校验，非法配置禁用该仓库的机器人并通知 owner

## 11. 里程碑

| 阶段 | 交付 | 验收 |
|---|---|---|
| **M0** 最小闭环 | GitHub App、webhook 验签与去重、任务表、拉起 pi-host 跑一个写死的技能，只产出不写入 | 一条真实事件端到端跑通，GitHub 侧零副作用 |
| **M1** 分类与合规（含首周观察期） | 6.1、6.2、标签与评论执行器、只读任务容器档；首周强制 dry-run 校准 prompt | 20 条历史 issue 回放，与人工标注比对 |
| **M2** 命令面与运行时保险 | 6.4 命令注册表与鉴权、10 秒应答、`/review-pr` 真实检出与测试；三层超时、重试矩阵、重复输出熔断同批交付 | 3 个真实 PR 结论可复现；人为制造的 429 与死循环被正确熔断 |
| **M3** 面板与主动建 issue | 6.5 只读视图与审计、6.3 去重与配额 | 面板数字与 DB 一致 |
| **M4** 写回升级 | 默认 auto 的 `push_branch` + 开 PR；不合规关闭走条件闸门 | 关闭路径不被错触发；分支可整体回收 |

每阶段以「仓库开关 + dry-run」交付，dry-run 永久保留。

## 13. 技术方案的输入约束

技术方案阶段（下一阶段）需遵守：

1. 优先使用开源库与成熟实现
2. MVP 不为已有成熟方案的组件自己造轮子；无成熟库时才自行实现
3. 面板用 React + Tailwind CSS
4. 后端语言待定（候选 Go / Node/TypeScript），在技术方案中给出结论与理由

技术方案需要明确回答：进程与部署形态、队列与持久化选型、agent 调用方式（RACP vs in-process）、GitHub App 集成方式、容器编排、面板数据来源、可观测性与密钥管理。
