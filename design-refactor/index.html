下面四份是选型时的对照稿（保留做记录）

A 经典侧栏控制台 密度优先 打开 →
赌：熟练运维，导航位置稳定、同屏信息最多。208px 左栏 + 顶栏 + 1fr/318px 双栏，KPI 压成一条六格。
B 顶部主轴 · 宽单列 阅读优先 打开 →
赌：一天只开几次，每次从「今天发生了什么」开始读。一句话摘要先行，区块用留白和 hairline 分隔而不是卡片。
C 主从双栏 · 收件箱 处理优先 打开 →
赌：90% 时间在处理一件具体的事。全局数字退成 32px 状态带，屏宽全给「队列 + 当前这条」，j/k 连续处理。
D Bento 网格监控墙 全局优先 打开 →
赌：多数时间在一眼扫全局、偶尔投大屏。12 列网格瓦片，导航收进底部 dock，最急的一块用反色瓦片。

四个方案怎么选

维度 A · 侧栏 B · 顶部单列 C · 主从 D · Bento
首屏能回答什么 全部：待办、KPI、趋势、活动 一句结论 + 关键数字 队列有多长、当前这条为什么停着 全局态势，每块都能单独看
同屏信息量 最高 中等 中等（一深一浅） 高（分布在各瓦片）
跳转成本 1 次点击 1 次点击（≤6 项） 列表内 j/k 不跳页 dock + 页内滚动
连续处理多条的效率 差（每次都要回总览） 差 最好 差
深链接 / 可分享性 好 好 好（选中项进 URL） 弱（一屏多对象）
迁移成本（现有 panel） ≈0：就是现状 中：导航表拆两级、页面改单栏 高：详情要能独立成页，路由要双形态 高：每个模块要声明尺寸，新增块要重排
最适合的场景 每天看很多次、窗口够宽、要横向对比 低频巡检、要发给别人看、写周报 值班处理队列、事故复盘 大屏展示、多人围观、指标墙
主要风险 左栏吃掉 15% 宽；导航一多就膨胀 一级导航放不下第 7 项；长页要滚很久 看不到全局对比；图表没地方放 瓦片尺寸锁死内容；小屏退化严重
我个人的排序
C > A > B > D。这个面板的核心任务不是「看报表」而是「处理卡住的任务」， C 的形态最贴近；A 是唯一零风险的退路。
也可以不选
A 的壳 + C 的列表：左栏保留，仓库内的「工作台」换成主从双栏。 两套骨架并存，按页面选，比全站统一更省事。
四者共通的部分
令牌、状态四档、33px 行高、tabular-nums、等宽 ID、⌘K。 这些不该在重构里变——变了就不是布局对比，而是重做设计系统。
文件：index.html（本页）、e-unified.html（采用方向）、对照稿 a-console.html、b-topbar.html、c-inbox.html、d-bento.html， 以及 assets/base.css（共用令牌与控件）与 assets/theme.js。
四个页面都支持深浅色（跟随系统，或打开 ?theme=dark）；都是静态演示，没有接 /api/*， 按钮不假装成功。
